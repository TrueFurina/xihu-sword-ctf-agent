## 1. AI 达克效应透镜：从认知偏差到机器镜像

### 1.1 原始理论：达克效应与"元认知双重诅咒"

Kruger & Dunning（1999）让被试完成逻辑推理、语法、幽默感等测试并自评百分位，数据显示：能力最差的四分之一群体实际表现仅约第 12 百分位，却自评约第 62 百分位；能力最高的四分之一实际约第 86 百分位、自评约第 74 百分位（[Atticus Li 综合评述](https://atticusli.com/replication-crisis/dunning-kruger-effect)、[RIOT IQ 综述](https://riotiq.com/articles/advanced-topics-and-research/what-is-the-dunning-kruger-effect-what-the-research-actually-shows)）。作者提出的机制是"元认知双重诅咒"：做好任务所需的技能与准确评价自身表现所需的技能是同一套技能，缺乏前者者同时缺乏后者——既不能胜任，也无法识别自己的不胜任；且该效应并非永久，训练提升技能后校准随之改善（[RIOT IQ 综述](https://riotiq.com/articles/advanced-topics-and-research/what-is-the-dunning-kruger-effect-what-the-research-actually-shows)）。

### 1.2 学术争议：统计伪影说与预注册研究

"低能者独特过度自信"的叙事很快受到方法学挑战。Krueger & Mueller（2002）认为，将广为人知的"优于平均水平效应"与回归均值相结合，无需任何元认知缺陷即可重现达克效应图形（[Atticus Li 综合评述](https://atticusli.com/replication-crisis/dunning-kruger-effect)）。Gignac & Zajenkowski（2020）基于 929 名被试的瑞文高级推理测验数据，改用连续回归与异方差（Glejser）检验，未发现显著异方差，能力与自评呈近似线性关系，论文标题直陈达克效应"（大部分）是统计伪影"（[论文记录页](https://ideas.repec.org/a/eee/intell/v80y2020ics0160289620300271.html)）；纯随机数据的模拟亦能完全复现该图形（[Atticus Li 综合评述](https://atticusli.com/replication-crisis/dunning-kruger-effect)）。2022 年 Hofer 等人在格拉茨大学开展的预注册研究（281 名被试、百分位式自评）显示，采用改进统计方法后仅言语智力仍保留显著效应（[PubMed 摘要](https://www.pubmed.ncbi.nlm.nih.gov/35225925/)）。据此，本报告将达克效应定位为"分析透镜"而非严格科学断言：其"能力与自知力同源"的核心洞见仍有解释力，但经典图形的幅度需打折扣。

### 1.3 LLM 过度自信：元认知的"内部-外部缺口"

对 LLM 的实证研究提供了更贴切的证据。Steyvers & Peters（2025）综述显示，模型具备真实的元认知敏感性（GPT-4 在 MMLU 上对错判别的自评 AUC 约 0.77–0.83），但存在"内部-外部缺口"：模型的内部概率往往"知道"自己可能出错，却无法在文本中如实表达；RLHF 对"果断、有帮助"回答的奖励进一步加剧了这一现象（[arXiv:2504.14045](https://arxiv.org/abs/2504.14045)）。Xu 等人在 ACL 2025 的实验中比较 Llama-3-70B-instruct、Claude-3-Sonnet 与 GPT-4o，发现模型对任务难度的敏感度低于人类，且以"专家/外行"等 persona 提示作答时，置信度随刻板印象漂移而准确率不变（[ACL Anthology](https://aclanthology.org/2025.findings-acl.1316/)）。

### 1.4 自我反思失效：为什么"再想想"反而更差

更关键的是自我反思的失效。Huang 等（ICLR 2024）证明，无外部反馈的"内在自校正"多数情况下无法改进、甚至恶化推理表现，此前报告的收益主要来自 oracle 标签；同等推理成本下多智能体辩论也不优于自洽采样（[arXiv:2310.01798](https://arxiv.org/abs/2310.01798)）。Snorkel AI 的实验数据显示，Claude Sonnet 4.5 在简单任务上经 5 轮自我批判后准确率从 98.1% 跌至 56.9%（0 例改善、8 例退化），机制是"批判幻觉"——批判者凭空捏造缺陷；而在困难任务上批判才起"调试器"作用（[Snorkel AI](https://snorkel.ai/blog/the-self-critique-paradox-why-ai-verification-fails-where-its-needed-most/)）。清华、南洋理工与蚂蚁集团的 ACL 2025 研究将反思失败归因于三种机制：内部答案波动（自我怀疑）、提示语偏差（失败时 76.1% 的注意力投向反思指令而非问题本身）、以及过度思考/认知过载等认知偏差，即使 o4-mini-high 也会在"地球是否平坦"这类简单事实上翻车（[论文解读](https://www.sohu.com/a/913782346_129720)）。

### 1.5 理论锚点：为什么"不知道自己不知道"

达克效应的机制解释与上述 LLM 现象共享同一内核：能力缺陷与元认知缺陷同源——"能力构建元认知"，缺乏能力者缺乏评价自身的可靠参照系（[RIOT IQ 综述](https://riotiq.com/articles/advanced-topics-and-research/what-is-the-dunning-kruger-effect-what-the-research-actually-shows)）。LLM 的过度自信与反思失效正是这一缺口的机器镜像：它们能生成流畅、果断的自信表达，却缺乏与真实能力挂钩的内部校准。

**点题**：上述机制共同预示了本项目"愚者巅峰"式的结局——赛前自评解出率 92.9%，赛时正式赛 64 题 0 解出；自信与能力之间如此极端的断裂，正是达克效应透镜下 LLM 元认知缺口的集中爆发（实证与治理见第 2–5 章）。

## 3. 多智能体失效机理：无锁并发与上下文断裂

### 3.1 无锁并发互踩实录

**论点**：本项目在 8/21–8/22 呈现的"多智能体"，不是框架内编排的并行，而是至少 6 个独立 LLM 会话（Session A–F）共享同一 `ctf_agent/` 工作树、在同一可变状态上无锁并发。互踩不是偶发事故，而是无写者隔离下的必然结果，也是初赛 0 解出根因链中"多进程互踩"的直接实证。

**论据**：[协同任务总账-TOP0.md](E:/Program/西湖论剑/协同任务总账-TOP0.md) 的会话代号表记录了 8/21–8/22 六个并发会话（A–F）在同一工作树上的全部操作，覆盖赛时排查、赛后大改造、锐评整改、git 重建与收口。互踩的极端证据链如下：
- **"单写者铁律 9:20 立、9:20 破"**：[2026-08-22 日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-22.md) 记录"AGENTS.md 单写者铁律成文于 09:20，违反于 09:20"——09:19–09:20 评审期间仓库仍在被并行会话提交，共 8 个 commit 落库（总账 [C3](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。
- **分支结构被并行删除**：Session C 提交 `011b0a0` 的同一分钟，另一会话执行 filter-repo 收尾删除整个 fix 分支，commit 变孤儿对象（[8/22 日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-22.md) 09:35–09:45 节）。
- **无租约改核心文件**：14:10 发现工作区出现 6 个 M 文件 + 2 个新测试（13:35–13:44 改动），违反 CTDE R1，pytest 203+1 FAILED（[总账 E26](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。
- **会话退出前未提交**：Session F 收口时发现 3 个 M 文件遗留 `tools/adapters/`，属典型"改文件不提交"（[总账 F7](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。
- **赛时同样发生**：[2026-08-21 日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-21.md) 记录并行会话曾误删 `scheduler/` 核心模块、`index.lock` 被并行会话占用导致无法提交。

**分析**：互踩的机制本质是**共享可变状态 + 无写者隔离**。多个 agent 各自持有独立的上下文窗口，对同一文件系统做出互不可见的写操作，任何一次覆盖/删除都对其他会话的"局部正确世界"造成破坏。总账史前段结论印证这不是单次失误：初赛根因（幽灵 base_url / get_access 字段错位 / 多进程互踩 / 403 WAF）在史前段反复修了又塌（[H9/H58/H63/H65/H68](E:/Program/西湖论剑/协同任务总账-TOP0.md)），正是无治理多会话反复踩同一坑的铁证。

### 3.2 git 对象库损坏事故

**论点**：无锁并发不仅踩文件，还直接破坏了 git 对象库本身——这使"多进程互踩"从工作树层上升到元数据层，造成比代码冲突更严重的历史完整性灾难。

**论据**：[8/22 日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-22.md) 完整记录了事故链（总账 [D6/D10/D16](E:/Program/西湖论剑/协同任务总账-TOP0.md)）：
- Session B 的 `git filter-repo` 重写历史（[B3](E:/Program/西湖论剑/协同任务总账-TOP0.md)）与另一会话的 `git gc` 并行执行，把对象 prune 成孤儿，main 的 tree 与若干 blob 恰在被清范围；
- 10:46 合并时 `git ls-tree main` 报 `fatal: not a tree object`，`git fsck --full` 实测缺失 **4811 个 missing blob**（reflog invalid 9713 条属 cosmetic）；
- 唯一可靠恢复源只剩工作区物理文件与 `_misc` bundle；损坏 `.git`（3.8G）整体移入 `_git_corrupt_backup_20260822/` 取证后 `git init` 重建为 19M，30+ 证据 commit 随旧对象库丢失。

**分析**：git 对象库是项目第二层共享可变状态，其一致性依赖"对象不可变、引用只能前进"的模型——但两个会话并行执行历史重写与垃圾回收时，各自的"引用前进"互相将对方的对象视为可回收垃圾。这与 [Gray & Cheriton 1989 年 Leases（SOSP）](https://web.stanford.edu/class/archive/cs/cs240/cs240.1226/readings/cs240-annot-leases.pdf) 所论证的共享资源一致性问题同构：多写者访问共享状态必须有带时效的授权（租约），否则"看起来无害"的维护操作（gc/prune）会摧毁对方的存活数据。

### 3.3 上下文断裂理论：为什么多智能体在这里是负资产

**论点**：本项目是 [Cognition《Don't Build Multi-Agents》（Walden Yan, 2025）](https://cognition.ai/blog/dont-build-multi-agents) 与 [Anthropic《Multi-Agent Research System》(2025)](https://www.anthropic.com/engineering/multi-agent-research-system) 所警告的失败模式的**极端实证**——比两者警告的场景更彻底地违反上下文工程原则。

**论据**：
- Cognition 提出两条原则：**原则 1 共享上下文**——每个 agent 的行动必须被系统其他部分的所有相关决策上下文告知，理想情况是"每个行动看到一切"；**原则 2 行动承载隐式决策**——并行 agent 基于未预先约定的冲突假设行动，冲突决策必然带来坏结果。结论是 2025 年多 agent 协作"只会产生脆弱系统"，默认应排除不遵循两原则的架构（[原文](https://cognition.ai/blog/dont-build-multi-agents)）。
- Anthropic 的 orchestrator-worker 实验给出量化代价：多智能体比单 agent 提升 +90.2%，但 token 消耗约 **15 倍**于普通聊天，且 token 使用量单独解释 80% 的性能方差；协调复杂度急剧上升（曾为简单查询生成 50 个子智能体、子智能体互相干扰）；其明确**不推荐用于大多数编码任务**——可并行化程度低、LLM 尚不擅长实时协调与委派（[原文](https://www.anthropic.com/engineering/multi-agent-research-system)）。
- 本项目的"多智能体"连 orchestrator 都没有：Session A–F 是进程外的独立 LLM 会话，无中央编排器、无统一规划，直接共享文件系统与 git 对象库（[总账会话代号表](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。它是 Anthropic 架构"去掉编排层"的版本，因此在协调开销上与 Anthropic 实测的 15× token 代价数量级相当（冗余 token 开销陡增），同时承受了全部编排缺失的后果——Session E 记录的并行会话"烧 token 自爆"（手搓 Z3 200 行 + bkcrack 坑 + 盲爆）即协调成本失控的实例（[总账 E5](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。

### 3.4 复合错误机理：三无叠加

**论点**：0 解出的"多进程互踩"不是单点故障，而是三个失效机制的复合叠加——**无锁（无写者隔离）+ 无验证（自校正无外部判据）+ 无协调（无编排/无身份/无门禁）**。

**机理一：共享可变状态无租约**。同一 git 工作树与同一 .git 对象库缺乏任何写者隔离，任何会话的写操作（文件覆盖、分支删除、gc/prune）都是对其他会话的潜在破坏（见 3.1 节、见 3.2 节证据）。

**机理二：隐式决策冲突**。每个会话基于自己的局部上下文做"局部最优"决策（Session B 大改造 1384→6156 文件[总账 B1](E:/Program/西湖论剑/协同任务总账-TOP0.md)、Session E 攻 ezip、Session C 锐评整改），但这些决策在共享文件系统上全局冲突；各会话看不到其他会话的上下文，直接违反 Cognition 原则 1，其局部最优行动的全局叠加即为冲突（[Cognition](https://cognition.ai/blog/dont-build-multi-agents)）。

**机理三：无外部验证器时自校正失效**。[Huang et al. (ICLR 2024)](https://arxiv.org/abs/2310.01798) 证明 LLM 在无外部反馈时无法进行内在自校正，多数情况下自校正后性能反而退化；[Snorkel 的"自我批评悖论"实验](https://snorkel.ai/blog/the-self-critique-paradox-why-ai-verification-fails-where-its-needed-most/)进一步量化：Claude Sonnet 4.5 在初始准确率 98.1% 的简单任务上经过 5 轮批评-改进循环后跌至 56.9%（↓41.2%），因为批评者会幻觉出不存在的问题。映射本项目：各会话的"自查自纠"（极致锐评驱动开发）与产出共享同一盲区，无法阻止 0 解出——赛前 92% 彩排（[2026-08-21 日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-21.md)）与史前段 92.9% 沙盒水位（[协同任务总账-TOP0.md](E:/Program/西湖论剑/协同任务总账-TOP0.md) 史前段核心结论）相对平台 0 accepted 的落差，正是"内在自校正"无外部验证器（平台 accepted 判据）时失效的实例。

**进程级细节（第 2 章仅概述，此处展开）**：赛时 8/21 有 5 个 race agent 进程 + 多会话并行，WorkBuddy Bash 残留的幽灵变量 `CTF_AGENT_LLM_BASE_URL` 覆盖正确端点（[A1](E:/Program/西湖论剑/协同任务总账-TOP0.md)），场上 5 个 agent 有 3 个错配并编造假 flag（[A3](E:/Program/西湖论剑/协同任务总账-TOP0.md)）；赛后 8/22 的互踩从"进程错配"升级为"历史重写对撞"（filter-repo vs gc，见 3.2 节）。五层根因链中"多进程互踩"正是这两种进程级冲突的统称。

### 3.5 小结

本章揭示了初赛 0 解出中"多进程互踩"的完整机理：失效不是单点错误，而是**无锁（无写者隔离的共享可变状态）+ 无验证（自校正无外部判据）+ 无协调（无编排、无身份绑定、无评审门禁）**三无叠加的复合错误。Cognition 的上下文断裂理论解释了"为何并行退化为互踩"，Anthropic 的 15× token 代价解释了"协调成本的失控"，Huang et al. 与 Snorkel 的自我批评研究解释了"为何自查自纠救不了 0 解出"。治理修复的具体机制（目录级写者租约、pre-commit 门禁、Reviewer 门禁如何落地）留待第 4 章展开——本章止于"为什么崩"。

## 4. 事后治理修复：租约、门禁与诚实化

### 4.1 论点

初赛 0 解出的根因链中，"多进程互踩"属于工程协同缺陷而非解题能力缺陷（[协同任务总账-TOP0.md](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。赛后 48 小时，项目围绕它建立了一套"契约—执法—审查"三层治理栈：8/22 上午 CTDE 协同协议落地，下午写租约机器化，8/23 凌晨升级为目录级多写者租约，随后叠加 pre-commit 多门禁与 Reviewer 评审门。这套治理解决了"谁在写、写哪里、写的是否诚实"三个问题，但其边界同样清晰：门禁只能拦截"形式错误"而非"语义错误"，机械门禁也不等于能力提升。

### 4.2 治理演进时间线——从"靠自觉"到"机器执法"

8/22 09:19-09:25 的极致锐评第三轮给出了治理的起点证据：门禁测试实测红（2 failed / 162 passed），且评审进行期间仓库仍被并行会话提交 8 个 commit——AGENTS.md 的"单写者铁律"成文于 09:20、违反于 09:20，从源头说明靠自觉的治理不可执行（[2026-08-22 工作日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-22.md)）。随后 CTDE 协议落地、`_lease.py` 写租约初版机器化（commit 62ee35b）。但 8/22 20:20 科研专家团 ARCH-1 实测判定：初版 `_lease.py` 是**单写者全局互斥锁**（coordination.json 仅单 session 字段），声称的"CTDE 分散执行"名不副实、并行实为串行，安全底座 8/10、作为协同范式 3/10、并行范式 NO-GO（[总账-ARCH-1](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。同日 20:2x G-激活会话进一步发现：pre-commit 事前门禁从未被 git 调用——`core.hooksPath` 改指 `git_hooks/` 后该目录只有 post-commit/post-merge，治理实为"事后记日志"而非"事前拦提交"（[8/22 日志 G-A1](E:/Program/西湖论剑/.workbuddy/memory/2026-08-22.md)）。8/23 02:35 G1 改造（commit ff8f5e7）将单写者锁升级为目录级多写者租约，随后 G2 身份登记、G3 收尾脚本、G4 写耦合度聚类在数小时内全部落地（[8/23 日志](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。

### 4.3 租约机制设计——以 Gray & Cheriton 1989 为理论锚点

G1 后的 `_lease.py` 将 coordination.json 改为 `{version, identity, leases}` 多租约映射，每个租约含 `scope / last_active / last_commit / ttl_min / lease_version`（[_lease.py](E:/Program/西湖论剑/ctf_agent/scripts/_lease.py)）。三个设计要点：其一，**目录级 scope 而非文件集合**——`scopes_conflict` 把 `agents/**` 归一化为 `agents/` 前缀做相交判定，A 持 `agents/**` 与 B 持 `skills/**` 可并行写，避免文件级锁的 scope 交叉死锁；其二，**双时间戳**——`last_active` 由 heartbeat/commit 续租、`last_commit` 用于归因与恢复点，`DEFAULT_TTL_MIN=30` 的 TTL 作为兜底，`is_stale` 判定 `now > last_active + ttl`，过期租约在 acquire 时**自动接管**；其三，**接管留痕（fencing）**——`--force` 或 stale 自动接管时写 `takeover_note`（如"接管 gu（stale 自动）"）并删除被接管方租约；`lease_version` 字段存在（docstring 声称"接管时自增"），但实际 `acquire` 写回恒为 0、未实现自增——这又是一处"文档声称与实现漂移"，恰是 ⑦文档一致性门禁要防的对象（[_lease.py:16/186/221](E:/Program/西湖论剑/ctf_agent/scripts/_lease.py)）。代码注释明确将 stale 自动接管锚定到租约理论："按 Lease 理论（Gray & Cheriton 1989：租约到期自动失效、资源可被重新分配）"（[_lease.py:203](E:/Program/西湖论剑/ctf_agent/scripts/_lease.py)）。该理论正是基于时间的容错机制：持有者崩溃后租约到期即失效，无需显式释放，这是对"多会话无锁并发 + 会话异常退出"最直接的解法（[Gray & Cheriton, 1989](https://web.stanford.edu/class/archive/cs/cs240/cs240.1226/readings/cs240-annot-leases.pdf)）。后续 `_acquire_lock` 又加入 PID 死锁检测：持锁进程已死时用 `os.replace` 原子覆盖抢占残留锁，根治 coordination.lock 反复卡死的老毛病（[8/23 日志 20:00 批三](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。

### 4.4 门禁体系——事前拦截与语义终审的分工

钩子体系（`scripts/hooks/pre-commit` + 独立 `commit-msg`）从最初的"密钥扫描+租约 scope"扩展为合计 **8 道机器门禁**。计数口径（按代码事实核对）：**「六门禁」指 `pre-commit` 脚本内置的六道 commit 级门禁**——①密钥扫描（P0-1 防回归）②诚实口径扫描（假水位短语即拒）③写者租约门禁（无 session 且无 `CT_AGENT_SINGLE=1` 默认拒绝，fail-closed）④git 身份绑定（commit author 必须等于会话 id，堵 P1-7 全仓同一 author 无法审计）⑥快速回归（防错体系 73 用例 <3s 机制自检）⑦文档一致性真实扫描（`_doc_consistency.py`，防"文档断言与实现漂移"）。**另两道机器门禁不在「六」内**：第 ⑤ 道 commit message 假水位拦截**不在 pre-commit 脚本内**，由独立 `commit-msg` 钩子承担（git 传 message 文件路径作 `$1`，比在 pre-commit 内猜 `COMMIT_EDITMSG` 位置可靠）；第 ⑧ 道 merge 全量门禁**不属于 commit 级门禁**——代码虽位于同一 pre-commit 脚本的 `MERGE_HEAD` 分支，但仅在 merge 进行中触发，强制全量 pytest。合计 = 六道 commit 级（pre-commit 内置）+ ⑤（commit-msg 钩子）+ ⑧（merge 级）= **8 道机器门禁**（[pre-commit](E:/Program/西湖论剑/ctf_agent/scripts/hooks/pre-commit)；[commit-msg](E:/Program/西湖论剑/ctf_agent/scripts/hooks/commit-msg)）。脚本头部注释自述"pre-commit 六门禁"但只编号到 ①-⑥、⑦⑧ 追加后未同步——这本身又是"文档声称与实现漂移"的一例。其上还有 Reviewer 评审门 `_reviewer_gate.py`：三项机器检查（pytest 全绿 + diff 全在租约 scope + 诚实口径），merge 前由**单点 integrator** 触发（[AGENTS.md 八、收尾冻结](E:/Program/西湖论剑/ctf_agent/AGENTS.md)）。设计哲学是"机器管形式上错（二值/事前/可回归），Reviewer 管语义上错（假解出/逻辑/正确性）"（[8/23 日志 T-09/T-10](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。

### 4.5 解题纪律运行时强制

并行会话攻 xuanhun_ezip 时绕开仓库现成 skill 手搓 200 行 Z3、再陷 bkcrack 版本坑、最终无方向盲爆，单题投入超过一整场比赛预算——根因是"把工程完备性当目标，忘了指标是解题数"（[AGENTS.md 第七节](E:/Program/西湖论剑/ctf_agent/AGENTS.md)）。修复分两层：合约层在 AGENTS.md 立 R1-R6 作战纪律；运行时层在 `core/prompts.py` 新增 `SOLVE_DISCIPLINE` 常量并注入 `build_plan_prompt` 末尾，每次解题动手前强制自检——R1 工具优先禁自研、R3 止损线 3 轮、R5 目标锚定 flag accepted、R6 成本核算"token = 比赛时钟"（[prompts.py:19-29](E:/Program/西湖论剑/ctf_agent/core/prompts.py)）。

### 4.6 效果证据

工程侧：pytest 从 8/22 的 208 passed 增长到 8/23 的 252 passed（[整改核查结论](E:/Program/西湖论剑/整改核查结论-20260822.md)；[8/23 日志 12:48](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)），门禁体系自身被测试覆盖；损坏的 `.git` 重建后从 3.8G 瘦身到 19M（重建副作用，[总账 D16](E:/Program/西湖论剑/协同任务总账-TOP0.md)）；8/23 coordination.json 实测出现 2 个并行会话租约（gu 持 `data/results`、另一会话持 `AGENTS.md`）各写不相交 scope——多写者并行从设计变为现实（[8/23 日志 G1 铁证](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。诚实侧：AGENTS.md 六、立"平台 accepted=0 唯一判据"，`_honesty_scan.py` 以短语+正则机器拦截假水位（"解出数 N→M 递增 / +N 真实解出"即拒）并区分使用-提及避免自指死循环，`test_no_false_waterlevel_in_active_docs` 防活跃文档假水位复发（[8/23 日志 10:16](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）；8/23 收敛纪律冻结"14/14、10732、specialcurve2 等均非 accepted"表述，钉死诚实基线：客场 49 题 27 解 = 55.1%，其中 74% 靠 presolve 直出；web 0/10 在该时点（14:56）被归因为"纯 LLM 短板"，但当晚 20:30 实测推翻该归因——主因是靶机基础设施问题而非 LLM 不会做 web（详见 4.7）（[AGENTS.md 终极收敛纪律](E:/Program/西湖论剑/ctf_agent/AGENTS.md)；[8/23 日志 14:56/20:30](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。

### 4.7 诚实局限：门禁解决"谁在写"，不解决"写的对不对"

三个必须写明的边界：其一，租约与门禁解决的是并发控制与形式验收，**语义正确性最终留给人**——`_reviewer_gate.py` 是最后一道，机器只做三查，终审靠人工 integrator（[8/23 日志 T-10](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。其二，治理一度是"纸面就位"——8/22 晚实测确认 pre-commit 事前门禁未激活（hooksPath 重构后未迁移），收口是 `cp scripts/hooks/pre-commit git_hooks/` + ROOT 路径修复（commit d69aea8），这本身是"文档声称与实现漂移"的 RDD 活例子（[8/22 日志 G-A1~G-A7](E:/Program/西湖论剑/.workbuddy/memory/2026-08-22.md)）；git pre-commit/commit-msg 本是工程标准机制，但钩子目录（`.git/hooks` 或 `core.hooksPath` 指定目录）须正确安装才生效，本项目的失效恰是"装了钩子≠钩子在跑"的典型（[Atlassian Git hooks 教程](https://cn.atlassian.com/git/tutorials/git-hooks)）。其三，**机械门禁 ≠ 能力提升**：8/22 冻结令颁布后仍有 58 个 commit（RDD 终局形态）；web 0/10 直到 8/23 晚修复靶机基础设施后才突破到 37/49=75.5%（web 0/10→10/10，presolve 直出 30 题）——解的提升来自工程修复与 presolve 直出，而非治理脚本本身；当晚 20:30 根因定位明确推翻早前"纯 LLM 短板"的归因：web 0/10 实为三层基础设施问题（靶机 127.0.0.1:9001 从未部署、presolve 入口 302 行过滤把无附件 web 题挡在门外、flag 不一致），教训是"先实测定位根因，别急着怪 LLM/加模板"；修复后暴露的下一个真实短板是 presolve 命不中的 19 题——纯 LLM 真解出仅 7/19≈37%（crypto7/misc6/reverse6）（[8/23 日志 19:00-20:30](E:/Program/西湖论剑/.workbuddy/memory/2026-08-23.md)）。

### 4.8 小结

治理的演进本质是从"事后记账"到"事前拦截"：以 Gray & Cheriton 的租约思想为理论锚点，用目录级多写者租约解决并发控制，用 pre-commit 多门禁 + Reviewer 门解决提交验收，用 SOLVE_DISCIPLINE 把解题纪律写进运行时。但它不解决"写得对不对"（语义正确性）与"能力够不够"（从 0 解出到 55.1%、修复基础设施后 75.5%，提升主要是工程与基础设施修复而非治理脚本）。机械门禁是治理的必要条件而非充分条件——这一边界为第 5 章的方法论启示埋下伏笔。

## 5. 可迁移方法论：如何不下山

本章把前四章的教训（92.9% 自评 vs 0 解出、0 解出根因链、RDD 循环病）抽象为可迁移给其他 LLM 工程与研究者的一般方法。核心主张：达克效应不是个人心理缺陷，而是**可以被工程化抵消的系统性偏差**——外部裁判、运行时纪律与规模控制三件套，是"从愚者巅峰下山"的路径。

### 5.1 诚实评估三原则

**原则一：外部裁判优先。** 真实环境 accepted、测试套件、工具返回值是唯一可信 KPI。Huang et al. (2024) 在 ICLR 的经典研究证明，LLM 在无外部反馈时几乎无法自我纠错推理，甚至越改越错；所谓"自我纠正"的提升几乎全部来自真实标签（oracle）的指导（[Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798)）。CRITIC 框架进一步确认"外部工具反馈显著优于纯自我纠正"（[CRITIC, ICLR 2024](https://arxiv.org/abs/2305.11738)）。本项目是反面教材的极端样本：赛前沙盒自评峰值 92.9%（29 题，非 accepted），正式赛 64 题 0 accepted——沙盒无真实裁判，所有自评数字在真实平台面前归零（[协同任务总账-TOP0.md](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。

**原则二：口径唯一性。** 单一判据 + 防假水位测试，杜绝沙盒/测试赛/正式赛口径混用。本项目的 92.9%、82.8%、测试赛 7/7 800 分均为非 accepted 口径，却反复被当作能力证据；更隐蔽的是 `or True` 恒真断言与 presolve 假阳性（`flag{--fa:""}`、`flag{C-02}` 等垃圾 flag 被标 `validated:true`）——恒真测试让"绿"失去意义（[第五轮修复作战计划-20260822.md](E:/Program/西湖论剑/第五轮修复作战计划-20260822.md)）。

**原则三：温室内外分离。** 本地离线"解出"必须显式标注非 accepted，不得进活跃文档。赛后整改落地了 `test_no_false_waterlevel_in_active_docs` 机器检查，禁止活跃文档出现无 accepted 依据的水位表述（[整改核查结论-20260822.md](E:/Program/西湖论剑/整改核查结论-20260822.md)）。诚实基线 8/23 客场 55.1%（27/49，本地离线）与 accepted=0 长期共存，靠的就是口径分离。

### 5.2 自校正纪律：从"自觉"到"运行时注入"

自我批评作为"第二意见"的价值取决于它依据什么。Nova Spivack 指出 AI 系统天然无法捕捉自身错误，因为错误恰恰产生于它自信之处（[Why AI Systems Can't Catch Their Own Mistakes](https://www.novaspivack.com/blog/why-ai-systems-cant-catch-their-own-mistakes-and-what-to-do-about-it)）；Snorkel 的"自我批评悖论"同样强调验证在需要处最脆弱（[The Self-Critique Paradox](https://snorkel.ai/blog/the-self-critique-paradox-why-ai-verification-fails-where-its-needed-most/)）。

本项目给出的工程答案是：把纪律从提示词里的建议升级为**运行时强制注入**。并行会话攻 xuanhun_ezip 时绕开现成 skill 手搓 200 行 Z3、又陷 bkcrack 坑、单题投入超过整场比赛预算的教训，被沉淀为 SOLVE_DISCIPLINE 六条（R1 工具优先禁自研、R2 假设先于实现、R3 止损线 3 轮、R4 信息优先于暴力、R5 目标锚定 flag accepted、R6 成本核算 token=比赛时钟），并注入 `build_plan_prompt` 使每次动手前必过一遍（[AGENTS.md](E:/Program/西湖论剑/ctf_agent/AGENTS.md)、[core/prompts.py](E:/Program/西湖论剑/ctf_agent/core/prompts.py)）。RDD 循环病的本质是"锐评驱动"替代"目标驱动"——锐评反馈循环产出的是文档与架构膨胀（1384→6156 文件、42 commit 约 60% 是擦屁股），而非解出数；防治靠"RDD 红线"：一轮迭代客场数字没动但 commit 一堆治理脚本即判定复发并回滚（[AGENTS.md](E:/Program/西湖论剑/ctf_agent/AGENTS.md)）。

### 5.3 多智能体协作边界

多智能体不是默认架构，而是有明确适用边界的工具。Anthropic (2025) 的实证显示 orchestrator-worker 模式在**广度优先、可并行**的研究任务上比单 agent 提升 90.2%，但代价是约 15 倍 token，且明确指出"多数编码任务可并行子任务较少，不适合多 agent"（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）。Cognition 则给出反向论证：子代理各自做出局部合理的"隐式决策"（风格、库选型）在全局冲突，编码等一致性敏感任务应坚持单线程线性 agent（[Don't Build Multi-Agents](https://cognition.ai/blog/dont-build-multi-agents)）。本项目的 CTF 解题恰是"写密集、一致性敏感"任务，多并发会话直接造成"多进程互踩 + 无租约改核心文件 + git 对象库损坏"三重事故（[协同任务总账-TOP0.md](E:/Program/西湖论剑/协同任务总账-TOP0.md)）。

若必须多 agent，本项目的治理给出两条可迁移原则：**租约解决"谁在写"，门禁解决"对不对"**。目录级写者租约源自 Gray & Cheriton (1989) 的经典 lease 设计——以 TTL 时间容错替代死锁，过期可强制接管（[Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency, SOSP 1989](https://web.stanford.edu/class/archive/cs/cs240/cs240.1226/readings/cs240-annot-leases.pdf)）；pre-commit 六门禁 + Reviewer 门禁则把"提交即验证"机器化，堵住"改不提交"的协议盲区。

### 5.4 项目规模警戒

Standish CHAOS 报告是规模风险的权威证据：2020 年仅约 31% 的软件项目成功、50% 延期/超支、19% 彻底失败，且**规模是首要失败因素**——grand 级项目成功率 6%，small 级达 61%（[Standish CHAOS Report 2020](https://budgetoverrun.com/studies/standish-chaos-report)）。本项目的危险模式与此同构：0 解出后不但未收缩，反而扩架构（1384→6156 文件）、扩文档（RDD 通胀），以"工程完备性"掩盖"解题数 0"的目标漂移（[第五轮修复作战计划-20260822.md](E:/Program/西湖论剑/第五轮修复作战计划-20260822.md)）。治理封板（不再新增治理脚本/文档）正是对规模膨胀的主动刹车。

### 5.5 未来研究方向

第一，LLM 元认知校准。Xu et al. (2025) 发现 LLM 对任务难度不敏感且过度自信，提出的 AFCE（将置信度估计与答案生成分离的两阶段提示）使 ECE 最多降低 63.8%（[Xu et al., Findings of ACL 2025](https://aclanthology.org/2025.findings-acl.1316/)）——这提示"让模型先报信心、再作答"可能比"自评解出率"更接近真实能力。第二，外部验证器自动化：Reflexion 之所以优于 Self-Refine，关键在于其失败信号来自外部（测试/环境）而非自我批评（[Reflexion vs Self-Refine vs CRITIC vs LATS](https://dreaming.press/posts/reflexion-vs-self-refine-vs-critic-vs-lats.html)），"build a verifier"比"improve the critic prompt"更根本。第三，多智能体协调协议的形式化：从租约（TTL 容错）走向可证明的并发协议。第四，"无人工干预多智能体协作"的可靠性边界：即便单步 95% 可靠，10 步顺序链完整成功概率仅约 59.9%，误差随 agent 数量复利（[Why Do Multi-Agent LLM Systems Fail?](https://agentswarms.fyi/blog/why-do-multi-agent-llm-systems-fail)）——规模越大，越需要验证器与止损机制。

### 5.6 小结：如何不下山

把"愚者巅峰"转化为"如何不下山"，工程答案是三件事：**外部裁判**（accepted/测试/工具返回值，而非自评）、**可证伪口径**（单一判据 + 防假水位机器检查）、**规模控制**（先止血后补血，治理封板，拒绝 RDD 通胀）。达克效应在此被去人格化：它不是某个 agent 太自信，而是系统缺少外部反馈回路时，自信必然膨胀到与真实能力脱节——补上反馈回路，就是下山的路。

## 结论

本报告的核心回答是：92.9% 的自评撞上 0 解出，并非某个 agent 过度自信的偶然失误，而是系统缺乏外部反馈回路时，自信必然与真实能力脱节的系统性必然。防达克效应的工程化路径可归纳为三条：**外部裁判优先、可证伪口径、规模控制**。

关键发现有四。其一，测量先于能力：在平台 accepted 唯一判据确立之前，任何"提升"都不可验证——赛前 92.9% 沙盒水位含 `or True` 恒真断言、假阳性 flag、本地离线误当战绩三类假水位（[第五轮修复作战计划-20260822.md](E:/Program/西湖论剑/第五轮修复作战计划-20260822.md)）。其二，无外部反馈的自校正必然失效：Snorkel 实验显示自我批判可使准确率从 98.1% 跌至 56.9%（[Snorkel AI](https://snorkel.ai/blog/the-self-critique-paradox-why-ai-verification-fails-where-its-needed-most/)），与赛前"内在自校正"无外部验证器时失效的实例同构。其三，多智能体的边界必须由机制界定：Anthropic 多智能体提升 +90.2% 但消耗约 15 倍 token，且不推荐用于编码类任务（[Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)）；本项目以目录级写者租约（[Gray & Cheriton, 1989](https://web.stanford.edu/class/archive/cs/cs240/cs240.1226/readings/cs240-annot-leases.pdf)）与 8 道机器门禁回应"谁在写"与"对不对"。其四，诚实化改造后，客场诚实基线 55.1%、修复基础设施后 75.5%，证明"measure first"带来真实增益。

未来方向应聚焦：LLM 元认知校准（AFCE 两阶段提示使 ECE 最多降 63.8%，[Xu et al., ACL 2025](https://aclanthology.org/2025.findings-acl.1316/)）、外部验证器自动化（"build a verifier"优于"improve the critic prompt"，[dreaming.press](https://dreaming.press/posts/reflexion-vs-self-refine-vs-critic-vs-lats.html)）、多智能体协调协议形式化。在多步误差复利面前（单步 95% 可靠 × 10 步仅约 59.9%，[agentswarms](https://agentswarms.fyi/blog/why-do-multi-agent-llm-systems-fail)），规模控制不是保守，而是理性。
