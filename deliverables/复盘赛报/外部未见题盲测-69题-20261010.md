# 外部未见题盲测报告 · 69 题（2026-10-10）

> **为什么要做**：10-06 交付的"外部基准"复核后发现能用于推理评测的只有 14 题、未见题仅 1 道（n=1，无统计意义）。本轮把分母换成**真正健康的题池**，重新做一个站得住的测量。
> **口径**：`INTERNAL_PRESOLVE=off`（纯 LLM 口径）+ `--presolve-skip` + E3 证据注入开；单题 token 上限 80K、墙钟 300s；判分走题面 `flag_sha256`（本项目 sha256 仲裁）。
> **题池构建（全部机器判定，无手挑）**：从 6 个外部池筛出「载荷完整 + 无答案泄漏 + 有可验真真值 + 未被解出/未进台账」的题，跨池同名 id 合并去重 → **69 题**（crypto 31 / rev 15 / misc 13 / forensics 10）。

---

## 一、先说两个必须记住的坑

### 坑 1：provider 掉线会让"能力数字"变成基础设施数字
第一轮用 deepseek 跑 69 题，**39 题死于 `provider_circuit_open`**（熔断）——那不是能力失败，是 provider 中途掉线。事后探测快照证实：当时可用 provider 仅 glm / xfyun。
**纪律**：任何跑批报告必须先说清"多少题获得了有效测量"，否则 53% 这种数字会被误读成能力。

### 坑 2：引擎解出 ≠ LLM 解出
第一轮有效测量 30 题解出 16（53.3%），但拆开看：
- **14 道是"放弃前确定性兜底"解出来的**（LLM 先失败放弃，确定性层最后一刻 crack）；
- **纯 LLM 独立解出只有 2 道**。

也就是说，如果只报"引擎解出率 53.3%"，等于把 LLM 能力**虚高 7 倍**。这两个数必须分开写。

## 二、测量结果（两轮，均被门禁判定为"不可用于能力口径"）

| 轮次 | provider | 有效测量 | 解出 | 确定性兜底 | LLM 独立 | tokens | 门禁判定 |
|------|----------|---------|------|-----------|---------|--------|---------|
| 轮 1 | deepseek-chat | **30 / 69**（39 题熔断未测） | 16 | **14** | **2** | 97,312 | ❌ 基础设施失败 56.5% |
| 轮 2 | xfyun（星火） | 69 / 69 | **0** | 0 | 0 | 818,125 | ❌ 89.9% 预算耗尽 |

**轮 1 的正确读法**：引擎整体在有效样本上 53.3%，但**纯 LLM 独立解出只有 2 道**（`babycrypto`、`lowe`），另外 14 道是"放弃前确定性兜底"解出来的。若只报 53.3%，等于把 LLM 能力**虚高 7 倍**。
有效样本内的失败结构：`unresolved` 8 / `extract_fail` 5 / `wallclock_killed` 1。

**轮 2 的失败形态**：xfyun 在 235 步里 **0 次"代码兜底恢复"**（JSON 解析失败且内容里没有可救的代码块），全程规划/推理直到预算耗尽（62 题 `budget_exceeded`）。
> ⚠️ 更正（2026-10-10 复核）：本文初稿写的是"0 次工具调用"，那是**统计口径用错 grep 词**（日志里执行痕迹用的是"代码动作兜底/沙盒"等词，而非 `tool:`）。按正确口径重述如上——结论方向不变（xfyun 基本不产生有效动作），但数字口径必须以此为准。

**轮 3（glm-4-flash，3 题探针）**：0 解出、105K token、1 题墙钟超时 + 2 题预算耗尽。
**它比 xfyun 好在确实产生了动作**（4 次代码围栏兜底恢复成 script 动作），但**单步 plan 超时 60s**（日志明确记录），慢到把预算烧光。

### 本轮结论（诚实版）

**当前无法给出可信的"外部未见题 LLM 能力数"。** 两个可用的 provider 各有一种失效：
- deepseek：**HTTP402 余额不足**（探测快照实证），跑到一半熔断，56.5% 的题没测到；
- xfyun：健康但**不会驱动工具循环**，0 解出。

**唯一能站得住的数字是第一轮那 2 道**：`LLM 独立解出 2 / 有效测量 30`，且必须注明
"同题集在另一 provider 上 0 解出，样本 30、单轮、无方差估计"。

### 复跑前置条件（已写成门禁）

1. `python scripts/_run_validity_guard.py --provider-check <name>` → provider 不健康直接退出码 3，禁止开跑；
2. 跑批后 `python scripts/_run_validity_guard.py --results-dir <dir>` → 基础设施失败超 20% 或"解出全来自确定性兜底"即退出码 2，**结果不得引用其解出率**。

> 附带发现：探测快照显示 deepseek 早在跑批开始前就已是 402——**跑批前置检查本该拦住这次整轮污染**。门禁已补。

### 三家 provider 横向对照（同一引擎、同一基准、纯 LLM 口径）

| provider | 能否产生有效动作 | 战绩 | 主要失败形态 |
|----------|----------------|------|-------------|
| **deepseek-chat** | ✅ 正常驱动工具循环 | 有效 30 题解 16（兜底 14 + LLM 2） | 中途 **HTTP402 余额不足** → 39 题熔断未测 |
| xfyun（星火） | ❌ 基本不产生（代码兜底 0 次） | 0 / 69 | 62 题预算耗尽（235 步只在规划） |
| glm-4-flash | ⚠️ 部分产生（兜底 4 次）但极慢 | 0 / 3 | 单步 plan 超时 60s → 1 题墙钟 + 2 题预算耗尽 |

**结论**：当前**只有 deepseek 能真正驱动这个 agent 循环**，而它余额不足。
其余两家的问题一半在模型（不产动作/太慢），一半在我们侧可改善（动作解析容错已具备：
`_extract_json_object` 括号平衡 + 围栏剥离 + `_repair_json`，代码兜底 4 次生效即证据）。
**因此提升路径是"换模型或充值"，不是继续改解析器**——解析器该救的已经救了。

## 四、局限（必须随数字一起引用）

1. **单模型单轮**：本轮只跑一个 provider、一轮，无重复实验 → 无方差估计。
2. **题池偏斜**：69 题以 crypto（31）与 reverse（15）为主，web/pwn 几乎缺席（外部池里 web/pwn 题多数落在"答案直读"层被剔除），**结论不能外推到 web/pwn**。
3. **"未见"判定依赖台账**：排除依据是 KPI 授权集合 + 已解出 ledger + 历史跑批报告中 solved 记录；若有跑批未落盘，个别题可能实际已见过。
4. **确定性兜底仍在链路里**：本轮只关了题首预扫，"放弃前确定性兜底"与技能强制路由仍参与，所以"LLM 独立解出"是**下限**。

## 六、provider 选型：多样本归档结论（2026-10-10 补，替代单题探针）

单题探针（`_provider_toolcap_probe.py`）证据不足——同一道题上 glm 与 xfyun 都是
0 解析失败 0 解出，说明"解析失败率"更像题目相关而非 provider 绝对属性。
故改用**已付费历史跑批离线聚合**（`scripts/_provider_capability_archive.py`，
扫 39 个 run，**零 LLM 调用、零新增成本**）：

| provider | 样本 | 有效测量 | 基础设施失败率 | **LLM 独立解出率** | 题均 token |
|----------|------|---------|--------------|------------------|-----------|
| **deepseek** | 213 题 / 10 跑批 | 174 | 18.3%（HTTP402） | **10.9%** | 58.3K |
| xfyun 星火 | 70 题 / 1 跑批 | 70 | 0% | **0%** | 51.9K |
| glm-4-flash | 39 题 / 3 跑批 | 39 | 0% | **0%** | 42.1K |
| kimi | 2 题 | 1 | 50% | 0% | — |
| (unattributed) | 36 题 | 36 | 0% | 8.3% | 11.4K |

**结论**：多样本下**只有 deepseek 有非零的 LLM 独立解出**，另两家均为 0——
单题探针的"两家都 0"其实是真结论，只是当时样本不足以区分。
**推荐 deepseek，其 18.3% 基础设施失败率全部来自 402 余额不足，充值是前置条件。**

### 归档聚合踩掉的三个坑（都是"数字好看但结论无效"）

1. **归属不明桶一度成为推荐对象**：靠 run 目录名猜 provider，而最大的两个 run
   （69 题 / 78 题）目录名里没有 provider 字样 → 全部落进 `unknown` 桶（253 题=最大桶），
   而它的 LLM 独立率 0.107 恰好**全场最高**——数字最漂亮、实际无归属。
   已修：显式 run→provider 映射 + `unknown` 标 `unattributed` 且排除出推荐。
2. **引擎有已知 bug 的历史轮次混算**：9-19 那轮跑在 P0 验证器 bug 修复**之前**
   （当日 1/10 实为冤案，修复后同协议 4/10）。混算等于把一个失效引擎版本的能力
   算进 provider 表现。已单列 `legacy_runs_excluded`。
3. 🔴 **生产 bug：`(x or 1)` 的 falsy 陷阱**——基础设施失败率恰为 `0.0` 时
   `0.0 or 1` → 1，"零失败"被当成 100% 失败，**所有 provider 全被拒、推荐恒为 None**，
   表现为"看起来很保守"的假保守。**这个 bug 是被变异测试逼出来的，生产侧自己没看出来**；
   而且它**掩盖了另一个变异体的表现**（M1 是否被杀死一度判错），教训是：
   两个变异体同时存在时先修掉会掩盖另一个的那个，否则会误判生产代码。

### 口径红线（引用本表前必读）

- **LLM 独立解出率 ≠ 引擎整体解出率**：引擎有"放弃前确定性兜底"，10-10 实测
  引擎 53.3% vs LLM 独立 6.7%——混报会把 LLM 能力虚高 7 倍。
- **题目跨 run 可能重复计入**：本表统计的是"该 provider 在历史跑批中的总体表现"，
  不是严格去重的独立样本；deepseek 的 213 题含同题多跑。
- `unattributed` / `low` / `insufficient` 三档**不参与推荐排序**（样本量或归属不达标）。
- 单题探针脚本保留为**准入前置**（新 provider 上线前先验它能否驱动工具循环），
  但**不作为选型依据**。
