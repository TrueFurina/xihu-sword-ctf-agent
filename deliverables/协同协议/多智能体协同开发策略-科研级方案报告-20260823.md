## 引言

大型语言模型（LLM）驱动的多智能体系统，正在把软件开发从「单人单会话」推向「多独立智能体并行协作」。Anthropic 的工程实践表明，多 agent 协作较单 agent 提升 90.2%、但 token 消耗放大约 15 倍（[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)）；Cognition 则给出反向主张——「写保持单线程、只读子 agent 并行」（[Cognition](http://www.cognition.ai/blog/multi-agents-working)）。两派分歧最终收敛到同一个难题：当多个独立 LLM 会话同时写同一份代码仓库时，如何在不引入中央编排器的前提下，保证并发安全、身份可信与贡献可归因。

本报告以 CTF-Agent 项目为对象，研究去中心化多智能体协同软件开发。该项目以 N 个独立 LLM 会话共享同一 git 工作树、无中央编排器的方式运行，构成「去中心化多智能体」的最小真实样本；其初赛 62 题 0 解出的真实战绩，则暴露了「多会话无锁并发」的代价。报告沿五条脉络展开：多智能体并行开发的理论基础与可迁移先例（第 1 章）、CTF-Agent 协同治理现状与四类缺陷的根因诊断（第 2 章）、去中心化协同的关键设计决策与理论锚点映射（第 3 章）、协议全栈设计（第 4 章）与实验设计及可发表性评估（第 5 章）。

核心发现是：现有「单写者全局互斥锁」把 N 会话压成串行 1×，是主要瓶颈；而 Stanford DeLM 已证明去除中央编排器可在 SWE-bench 上取得 +10.5% 的提升且成本 -50%（[VentureBeat](https://venturebeat.com/orchestration/stanfords-delm-cuts-multi-agent-task-costs-50-without-a-central-orchestrator)），佐证了去中心化路线的可行性。本报告据此提出「目录级多写者租约 + 签名身份 + 贡献加权」的三层协同协议，并给出可对照初赛基线的实验证伪方案。

## 1. 多智能体并行开发的理论基础与可迁移先例

**论点**：把"多个独立 LLM 会话在同一 git 仓库并行开发、无中央编排器"放入已知解法坐标系后发现，该命题落在三条理论脉络的交叉点——LLM 协作机制谱系、分布式并发控制、MARL 归因理论；其中 git-native 协议（GNAP）与去中心化拜占庭鲁棒协议（SAC/DecentLLMs）已为"无中央编排器"提供可迁移先例。

### 1.1 三条理论脉络

**(1) LLM 协作机制谱系。** 现有协作范式大致可归为三类。其一为主从式 orchestrator-worker，如 Anthropic 工程报告（[机构](https://www.anthropic.com/engineering/multi-agent-research-system)）以 Claude Opus 4 主导、Sonnet 4 作子 agent，较单 agent 提升 90.2%。其二为辩论式，如 Multiagent Debate（[学术，Du et al. 2023, arXiv:2305.14325](https://arxiv.org/abs/2305.14325)），GPT-3.5 辩论提升算术与事实性问答表现。其三为 SOP 流水线式，如 MetaGPT（[学术，arXiv:2308.00352](https://arxiv.org/abs/2308.00352)）以五阶段装配线组织，SoftwareDev 达 100% 完成率、HumanEval 85.9% pass@1，以及 ChatDev（[学术，ACL 2024](https://aclanthology.org/2024.acl-long.810/)）。

三者的共性在于：**并行度越高、去中心化越强，token 代价与一致性风险同步上升**。主从式靠中央 orchestrator 调度多个并行子 agent，多轮来回的协调产生 token 开销，且中央点是单点瓶颈、也是一致性信息的汇聚处；辩论式让多个 agent 并行作答再汇总，agent 数量越多 token 消耗越大，而"多数收敛"依赖诚实多数的前提；流水线式把任务切成多阶段并行装配，阶段间接口协议一旦出现偏差就会被逐级放大。换言之，三类范式都在"去中心化收益"与"协调成本"之间做权衡，而其共同前提仍是存在某种显式或隐式的协调者。

**(2) 分布式并发控制。** Gray & Cheriton 1989 的 Lease 机制（[学术](https://dl.acm.org/doi/10.1145/74850.74870)）通过租约到期自动失效，使持锁者崩溃时不致死锁；乐观并发在 git merge/rebase 中天然存在，GNAP 的冲突解决即建立于此（[行业/开源](https://zread.ai/farol-team/gnap/12-conflict-resolution)）；资源分区的吞吐可达 N×，而全局互斥仅为 1×——这条"分区换吞吐、互斥换安全"的权衡线，正是"多写者并行写同一仓库"命题的底层约束。

**(3) MARL 归因理论。** CTDE（集中训练、分散执行）依赖 critic、价值函数与回合奖励完成信用分配（[行业/知识库](https://emergentmind.com/topics/centralized-training-decentralized-execution-ctde)），而代码协作中三者皆无，故 CTDE 只能作类比、不能作部署范式；可用的归因工具是 Shapley 值三公理（[学术，Rozemberczki 2022, arXiv:2202.05594](https://arxiv.org/abs/2202.05594)）。

### 1.2 可迁移先例

GNAP 把 git 当作协调基底（[行业/开源](https://zread.ai/farol-team/gnap/13-git-as-coordination-substrate)），用 agent/task/run/message 四类 JSON 加心跳循环维持状态；task claim 竞态以 git non-fast-forward 拒绝再 pull/rebase/retry 处理（[行业/开源](https://zread.ai/farol-team/gnap/12-conflict-resolution)）。SAC 采用去中心化 filter-and-refine 加 (F+1)-robustness（[学术，arXiv:2605.09076](https://arxiv.org/abs/2605.09076)）。DecentLLMs 由 worker 并行生成、evaluator 打分、几何中位数聚合，MMLU-Pro 达 71%（[学术，arXiv:2507.14928](https://arxiv.org/abs/2507.14928)）。

### 1.3 主流争议正反方

正方 Anthropic（[机构](https://www.anthropic.com/engineering/multi-agent-research-system)）报告 90.2% 提升，但 token 代价 15×（token 解释了 80% 方差）。反方 Cognition（[机构](http://www.cognition.ai/blog/multi-agents-working)）主张写代码走单线程、只读子 agent 并行。中立侧 SWE-agent（[学术，NeurIPS 2024, arXiv:2405.15793](https://arxiv.org/abs/2405.15793)）以"单 agent + 定制 agent-computer interface（ACI）"而非多 agent 编排，在 SWE-bench 全量达 12.47%、Lite 达 18.00%、HumanEvalFix 87.7% pass@1，其核心结论是接口设计（而非增加写者数量）才是首要工程问题——这一单线程路线与 Cognition 的主张相互印证，也与 EnIGMA（[学术，arXiv:2409.16165](https://arxiv.org/abs/2409.16165)）NYU CTF >3× 的提升同源：两者都不是多写者并行带来的增益。关键数据 OpenHands 77.6% SWE-bench Verified（[行业/排行榜](https://www.sota2.com/research/sota/software-engineering-on-swe-bench-verified-resolution-rate)）同样未证明多写者并行的必要性。

### 1.4 分析

orchestrator/SOP 隐含中央协调者；辩论/SAC/DecentLLMs 针对"可验证答案 + 诚实多数"的问答场景，而非"共享可变代码库"的写冲突；GNAP 是唯一同构先例，但押注"冲突罕见"的乐观假设，未解决高争用下 rebase 后的语义正确性——这正是本课题的空白区。

### 1.5 小结

本命题的边界在于：既有 LLM 协作机制要么依赖隐含的中央协调者（orchestrator/SOP），要么只成立于"可验证答案 + 诚实多数"的问答场景，而非共享可变代码库的写冲突；而唯一同构先例 GNAP 押注"冲突罕见"，未触及高争用下 rebase 后的语义正确性。由此，空白区被锁定为：在无中央编排器的前提下，为多写者并行写同一 git 仓库提供可证明的冲突语义与归因。

## 2. CTF-Agent 协同治理现状与四类缺陷的根因诊断

### 2.1 现状：三层治理架构盘点

CTF-Agent 在维度二（开发协同策略）采用「无中央编排器、多独立 LLM 会话在同一 git 仓库并行开发」的形态。现行协同治理为三层结构 + 一个单一事实源：

- **原则层**《多智能体协同准则纲领》：10 条铁律，每条绑真实事故——机器强制优先（§1）、身份显式（§2）、写前持租约（§3）、在飞改动禁令（§4）、诚实产出（§5）、验证优先（§6）、冲突接管（§7）、终止信号（§8）、协调者职责（§9）、DoD（§10）。
- **规范层**《CTDE 协同协议》：角色分工（Centralized 协调者 / Decentralized 执行会话）+ R1–R5 硬规则 + TASK_BOARD 任务板 + 冲突仲裁表。
- **执法层**：`scripts/_lease.py`（写者租约）+ `git_hooks/pre-commit`（密钥扫描 + 租约 scope 双门禁）+ `git_hooks/post-commit`（自动记账，机器强制、无常驻进程）。
- **事实源**：`协同任务总账-TOP0.md`，post-commit/post-merge hook 自动追记每次提交。

这四层共同回答了「谁在写、写哪不冲突」两个问题；但「写对不对」的量化验收与「谁贡献了什么」的归因在现行实现中缺失——这正是四类缺陷的共同指向。

### 2.2 四类缺陷的根因诊断

**缺陷①（P0）`_lease.py` 是「单写者全局互斥锁」，不是「目录级多写者租约」。** 证据：`_lease.py:120` acquire 拒绝条件为 `cur and cur.get("session") != session and not is_stale(cur)`——只要 A 持任意 scope 且未过期，B 写任何目录都被拒。租约数据只存一个 `session` 字段（`_lease.py:134-143`）。关键细节：代码确实存了 `scope` 字段、也确有 `path_in_scope()` 匹配函数（`_lease.py:198-210`），但 scope 校验只作用于 owner **自己的**提交（越界拦截，`_lease.py:226-236`），acquire 环节**从未做 scope 相交判定**——scope「存而不用」于并发入口。后果：A 持 `agents/**` 时，B 连 `skills/**`、`data/**` 都写不了，N 会话并发被压成串行，吞吐从 N× 退化为 1×。根因：把「防冲突」简化为「一次只许一人写」，把「动作空间分区并行」降级为「互斥串行」。对照 Gray & Cheriton 的租约原义——租约按数据粒度授予、允许不同数据上存在多个独立租约（[Leases, 1989](https://web.stanford.edu/class/archive/cs/cs240/cs240.1252/readings/cs240-annot-leases.pdf)）——本实现把「多租约按 scope 分区」坍缩成了「单一全局租约」。

**缺陷②（P0）术语错用 CTDE。** 协议标题与正文自称「CTDE 范式」，并把 CTDE 重定义为「Centralized=单一协调者定任务分解，Decentralized=各会话在文件域内执行」。而 CTDE 在 MARL 文献中是**训练范式** Centralized Training with Decentralized Execution——训练期用集中 critic 学全局价值函数（解决信用分配与 non-stationarity），执行期各 agent 凭局部观测独立决策（[MADDPG, Lowe et al. 2017](https://arxiv.org/abs/1706.02275)；[QMIX, Rashid et al. 2018](https://arxiv.org/abs/1803.11485)）。它需要 critic、价值函数、回合奖励三要素；本项目代码协作**三者皆无**。根因：先起高级名字，再往里面塞内容——概念容器选错在先。

**缺陷③（P1）会话身份是裸字符串，无签名身份。** `git_hooks/pre-commit:33-36` 只做 `SESSION="${CT_AGENT_SESSION:-}"`，空则回退 `git config --get atomcode.session`——身份来源是任意字符串，无任何签名或密钥校验：可撞名、可冒充、无法审计。根因：无签名身份，「谁是谁」无法防伪。对照授权协议 GNAP 以绑定到客户端实例的密钥做认证（[RFC 9635](https://www.rfc-editor.org/rfc/rfc9635.html)），项目自身锚点 MARL-ECDSA 的 ECDSA CA-less 身份也早已给出答案——本实现是明显退步。

**缺陷④（P1）无贡献归因、无拜占庭防御。** 现有门禁是二值的（绿/红），post-commit 只做流水账记录，不做加权；协调者仲裁全靠人工裁决、无量化依据；无针对恶意 agent（搭便车、伪造提交、抢锁占坑）的防御机制。根因：缺 Shapley 式贡献加权与鲁棒共识（[Shapley 1953《A Value for n-Person Games》](https://www.rand.org/pubs/papers/P0295.html)）。

### 2.3 小结

四类缺陷可归纳为**一条主线、两个缺口**：一条主线是「术语先行、实现降级」——先借 CTDE 这个 MARL 概念，再降级成「单写者全局互斥锁」，「并行」名存实亡；两个缺口是「身份缺口」（谁是谁无法防伪）与「激励/防御缺口」（谁贡献多少、谁恶意无法判定）。治理方向正确（机器强制 > 自觉、诚实口径 > 自报、单一事实源）不掩盖核心机制名不副实。

## 3. 去中心化协同的关键设计决策与理论锚点映射

**决策① 并发策略：从「全局单写者互斥」改为「目录级多写者租约」。** 理论锚点 Gray & Cheriton 1989 租约——「非拜占庭故障只影响性能、不影响正确性」（[Leases, 1989](https://web.stanford.edu/class/archive/cs/cs240/cs240.1226/readings/cs240-annot-leases.pdf)）。正反论证：Anthropic 90.2%/15×token，但编码任务可并行子任务少（[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)）；Cognition 主张写单线程（[Cognition](http://www.cognition.ai/blog/multi-agents-working)）。调和：Cognition 反对的是「同一文件上的多写者 swarm」，而非「不相交目录上的并行」——目录级租约保证不同目录不交叠写、每个目录内单写者，与 Cognition 不矛盾。诚实局限：时钟同速假设、跨目录共享资源需额外规则、15×token 经济成本仍在。

**决策② 身份：从裸字符串改为 ECDSA CA-less 每 agent 密钥签名。** 数字签名提供认证/完整性/不可否认三保证（[Digital Signature](https://stealthcloud.ai/glossary/digital-signature/)）；GNAP 以密钥绑定做认证（[RFC 9635](https://www.rfc-editor.org/rfc/rfc9635)）。诚实局限：TOFU 信任锚、密钥生命周期管理；**何时才值得上 ECDSA**——威胁模型是「会犯错的队友」而非「恶意攻击者」时，唯一 ID + 登记绑定已足以解决撞名，签名是进阶而非必需。

**决策③ 术语与范式纠正：部署期协作协议 ≠ CTDE 训练范式。** CTDE 是训练/执行解耦的学习范式（[CTDE](https://www.emergentmind.com/topics/centralized-training-decentralized-execution-ctde)）。本项目没有「训练」阶段，要解决的是运行时资源竞争、身份与归因。术语纠正后，部署期以「本地可观测 + 归因反馈 + 无共享状态」替代 CTDE 的解耦收益——各会话凭本地观测（git diff + 总账）独立决策，靠租约与门禁维持全局一致性，而非集中 critic。

**决策④ 归因与鲁棒性：Shapley 贡献加权共识 + 分级惩罚。** Shapley 值提供满足效率/对称/哑元/线性四公理的唯一公平归因（[Rozemberczki 2022](https://arxiv.org/abs/2202.05594)）；PBFT 确立 3f+1 拜占庭容错结构（[PBFT](https://www.cube.exchange/what-is/pbft-practical-byzantine-fault-tolerance)）；重复博弈 folk theorem 表明「未来阴影」下合作可被持续（[Repeated Games](https://www.ideasthesia.org/repeated-games-cooperation)）。设计：CW-PBFT 三项分解权重 40% 任务 + 35% 协作 + 25% 合规（**标注为可调超参数，非理论定值**），投票权重 `w = 1.0 + 0.5 × score`；分级惩罚 WARNING→DEMOTED→BANNED（权重 1.0→0.3→0.0）。诚实局限：Shapley O(2^n) 需 Monte Carlo 采样近似（[Monte Carlo Shapley](https://www.emergentmind.com/topics/monte-carlo-shapley-value-estimation)）；归因权依赖「accepted 解出」数据，平台关闭时无法校准；3f+1 在弱威胁模型下偏重、可能过度工程。

**小结**：四个决策构成一条完整链条——**决策①分区**划定不交叠的写资源边界（租约），**决策②身份**保证每个写入者可验证（签名），**决策③范式**把问题正确定位到部署期而非训练期，**决策④归因**用加权共识与分级惩罚维持激励与鲁棒性。

## 4. 多写者租约、签名身份与贡献共识的协议全栈设计

本章定义目录级多写者协作的四层协议：租约协议（4.1）、签名身份协议（4.2）、贡献加权共识协议（4.3）、门控通信机制（4.4），并在 4.5 给出完整状态机、消息协议与异常处理。设计目标：在无中心协调器的 git 仓库上实现多 session 安全并行写入，且单点故障只影响单一 scope。

### 4.1 目录级多写者租约协议

**核心变更**：`coordination.json` 从单 session 独占改为多租约映射，将「写权」下放到目录（scope）粒度，允许多个 session 在不相交 scope 上并行提交。

**数据结构（JSON Schema）**：

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["version", "identity", "leases"],
  "additionalProperties": false,
  "properties": {
    "version": { "type": "integer", "minimum": 1 },
    "identity": {
      "type": "object",
      "patternProperties": {
        "^[a-z0-9][a-z0-9-]{7,63}$": {
          "type": "object",
          "required": ["public_key", "key_id", "registered_at"],
          "properties": {
            "public_key":  { "type": "string", "pattern": "^ed25519:[A-Za-z0-9+/=]+$" },
            "key_id":      { "type": "string", "pattern": "^[a-f0-9]{16}$" },
            "registered_at": { "type": "string", "format": "date-time" }
          }
        }
      }
    },
    "leases": {
      "type": "object",
      "patternProperties": {
        "^[a-z0-9][a-z0-9-]{7,63}$": {
          "type": "object",
          "required": ["scope", "last_active", "last_commit", "ttl_min", "key_id", "lease_version"],
          "properties": {
            "scope": { "type": "array", "minItems": 1, "uniqueItems": true,
                       "items": { "type": "string", "pattern": "^[A-Za-z0-9_*./-]+$" } },
            "last_active":  { "type": "string", "format": "date-time" },
            "last_commit":  { "type": "string", "format": "date-time" },
            "ttl_min":      { "type": "integer", "minimum": 1 },
            "key_id":       { "type": "string", "pattern": "^[a-f0-9]{16}$" },
            "lease_version": { "type": "integer", "minimum": 0 }
          }
        }
      }
    }
  }
}
```

**scope 相交判定（冲突解决核心）**：acquire 时将每个 scope 字符串展开为路径前缀集合（glob `**` 展开为目录前缀）；新租约 scope 集合与每个已有租约 scope 集合逐一比对，存在任一路径同时属于两者、或 p 是另一路径的前缀，则判定相交。相交 → 拒绝；不相交 → 放行。示例：A 持 `agents/**` 与 B 持 `skills/**` 可并行；A 持 `agents/**` 与 C 持 `agents/planner/**` 相交，需抢占或等待。

**scope 粒度确定**：用 git 历史文件共现矩阵聚类（写耦合度聚类），对应 [Gall et al. 1998 逻辑耦合](https://ieeexplore.ieee.org/document/738496)。共现矩阵：对每个 commit 中同时出现的文件对 (f_i, f_j) 计数 C_ij，归一化为 Jaccard 相似度 J_ij = C_ij / (C_i + C_j − C_ij)；对距离 1 − J_ij 做层次聚类（average-linkage），在距离阈值 θ=0.6 处截断得到 scope 簇；冷启动（无历史）默认按目录一级切分。

**双时间戳分离**：`last_active`（心跳续租，判定租约存活）与 `last_commit`（实际提交，用于归因与恢复点判断）分离，避免「活跃但无产出」误杀与「有产出但心跳丢失」误判。

**默认 fail-closed**：任何校验失败（签名不符、无租约、fencing token 过期）一律拒绝写入。

**fencing token**：由 `key_id`（会话密钥指纹）+ `lease_version`（租约版本）组成，拦截过期节点迟到写——思想源自 [Chubby, Burrows 2006](https://static.googleusercontent.com/media/research.google.com/en//archive/chubby-osdi06.pdf) 的 sequencer：被 take_over 的旧写者即使网络恢复后迟到，其携带的旧 lease_version 已小于当前值，写入被拒。

### 4.2 签名身份协议

会话本地生成 Ed25519 密钥 → 公钥注册到 identity 表 → commit 用 SSH 签名（[GitHub Signing commits](https://docs.github.com/en/authentication/managing-commit-signature-verification/signing-commits)，Git 2.34+）→ pre-commit 钩子校验「签名会话 == 租约会话」。

异常处理路径：公钥与会话不符 → pre-commit 拒绝；密钥丢失 → 走轮换（新密钥注册 + 旧 key_id 标记 revoked + lease_version+1 使旧 fencing token 失效）；无租约提交 → fail-closed 拒绝。

### 4.3 贡献加权共识协议

双权重分离：**merge 权**（验证通过提交数，可计算）≠ **归因权**（accepted × 难度，无数据不校准）。任务总账作为单一事实源，采用 [GNAP](https://github.com/farol-team/gnap) 的 `tasks/+runs/` 结构。归因权校准触发条件：累计 accepted 任务数 ≥ N_min（初设 30）+ 覆盖 ≥3 难度档 + 每档样本 ≥5；校准前归因权不参与 merge 决策。

### 4.4 门控通信机制

（映射 [COCOM, Li et al. AAAI-25](https://doi.org/10.1609/aaai.v39i22.34490) 隐式共识）会话间不直接消息通信，通过 git 仓库 + 任务总账隐式同步；显式广播仅限「终止信号 TERMINATE / 阻塞升级 ESCALATE」两类门控消息，避免 O(N²) 广播风暴。其余一切同步均走隐式通道（git 提交 + 总账 diff）。

### 4.5 完整状态机与消息协议

**消息格式（四类）**：

| 消息 | 方向 | 字段 | 触发 |
|---|---|---|---|
| acquire | session → 协调层 | session_id, scope[], ttl_min, key_id, lease_version, public_key | 会话启动/需新 scope |
| heartbeat | session → 协调层 | session_id, key_id, lease_version, last_active | 每 heartbeat_interval |
| release | session → 协调层 | session_id, key_id, lease_version, scope[] | 正常结束/释放 |
| fence | 协调层 → 过期写者 | session_id, stale_lease_version, current_lease_version, reason | 检测迟到写 |

**租约状态机（含触发条件与动作）**：

| 转移 | 触发条件 | 动作 |
|---|---|---|
| idle → acquired | 收到 acquire 且 scope 与现有租约不相交 | 写入 leases[session_id]，lease_version=0 |
| acquired → active | 首次 heartbeat + 公钥校验通过 | 更新 last_active |
| active → active | 每次 heartbeat / 每次 commit | 更新 last_active / last_commit |
| active → stale | now − last_active > ttl_min | 标记 stale，允许 take_over |
| stale → taken_over | 其他会话 acquire 相交 scope 且已超时 | 抢占者 lease_version+1，旧 key_id 失效 |
| → released | 会话主动 release | 删除 leases 条目 |

**TTL 与心跳**：TTL ≥ 3 × 心跳间隔（[Lease 模式综述](https://hackernoon.com/building-distributed-leases-with-consensus-heartbeats-and-fencing-tokens)）；参照 K8s 的 15s/10s/2s，本协议默认 ttl_min=15、heartbeat_interval=5、retry=2（分钟，可按仓库规模调整）。

**fencing 校验步骤**：① 写者提交时附带 fencing token；② 接受前读取当前 lease_version；③ 写者 lease_version < 当前值 → 拒绝；④ key_id 不在 identity 表或与 leases 不符 → 拒绝；⑤ now − last_active > ttl_min → 视为 stale，拒绝并要求重新 acquire。

**拜占庭处理（分模型表述，不可混用）**：租约层用签名认证 + fencing token（非共识投票，不涉及 f 界）；结果层用拜占庭鲁棒聚合（几何中位数），适用诚实多数界 **f < n/2**（[DecentLLMs](https://arxiv.org/abs/2507.14928)）；未来若引入「异步共识投票式 merge」，才需 PBFT 界 **f < n/3**（n > 3f）（[PBFT](https://www.cube.exchange/what-is/pbft-practical-byzantine-fault-tolerance)）；同步模型 + 签名认证（Dolev-Strong）的 n > 2f 界本协议当前未采用。

## 5. 方案验证的实验设计与可发表性评估

### 5.1 评测指标与目标阈值

吞吐（相对单写者 1× 的倍数）、写冲突率、归因准确度、token 效率（协同层额外 token 占解题总 token 比例）、拜占庭鲁棒性。token 效率独立为第一类指标（[Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system) 测得 token 解释 80% 方差；[arXiv:2604.22750](https://arxiv.org/abs/2604.22750) 表明 agentic 编码 ~1000× token 且 token 越多 ≠ 准确率越高）。

为使「协议是否有效」可证伪，5 项指标各设目标阈值，共同构成 Wilcoxon 符号秩检验的备择假设（H1）：

| 指标 | 目标阈值（H1） | 依据 |
|---|---|---|
| 写冲突率 | 相对无租约基线下降 ≥50% | 目录级租约应显著减少互踩 |
| token 效率（协同层额外 token 占比） | ≤1% | 租约是文件系统元数据锁，非 LLM token |
| 归因准确度 | ≥95% | ECDSA 签名理论可 100% 验证，留 5% 容错 |
| 吞吐（相对单写者 1×） | ≥2× | 证明目录级并行带来真实吞吐提升 |
| 拜占庭鲁棒性 | 注入 30% 恶意 agent 后正确率 ≥90% | 诚实多数假设 f < n/2 |

### 5.2 基线对比

15× 成本四大来源（[Augment Code](https://augmentcode.com/guides/multi-agent-cost-compounding)）。二维平面定位：横轴 = token 成本、纵轴 = 吞吐，最优区间 = 高吞吐低 token 的右上角。

- **单 agent ≈ 4×**（[Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system) 一手实测 + [Augment Code](https://augmentcode.com/guides/multi-agent-cost-compounding) 成本拆解）
- **orchestrator ≈ 15×**（同上来源）
- **单写者 = 1×**（本项目基线定义：全局互斥锁串行化，吞吐上限即 1×）
- **GNAP = 无锁**（协议机制分析：协调成本 = git 提交 + 心跳文件，无 LLM token 开销）
- **本项目目录级多写者租约** → 落最优区间（轻量元数据锁，[GitLab File Locking](https://docs.gitlab.com/user/project/file_lock/)、[Git LFS](https://github.com/git-lfs/git-lfs/wiki/File-Locking)）

[Stanford DeLM](https://venturebeat.com/orchestration/stanfords-delm-cuts-multi-agent-task-costs-50-without-a-central-orchestrator) 去中央编排器 SWE-bench +10.5%、成本 -50%，佐证「编排器本身就是成本中心」。

### 5.3 实验设计

配对非参设计，对照组 = 初赛 3 天无租约（62 题 0 解出 + 互踩，**本项目初赛真实平台实测、内部记录，非假设**），实验组 = 同题库装租约重跑；因变量 = 冲突次数 / 返工 commit / 有效 merge / 每题耗时 / 并行存活租约数；Wilcoxon 符号秩检验（备择假设 H1 = 5.1 节 5 项阈值）+ bootstrap；拜占庭注入单独实验（注入 30% 恶意 agent）；基线锚点 [EnIGMA](https://arxiv.org/abs/2409.16165) 13.5%、[Cybench](https://cybench.github.io/) 40 题。

### 5.4 威胁有效性

内部效度：控制熟练度混杂、模型非确定性（[arXiv:2604.22750](https://arxiv.org/abs/2604.22750) 测得同任务 token 消耗可差 30×，故需 30× 重复取中位数）。外部效度：CTF 高度独立可并行，推广一般软件开发存疑须声明适用边界。构念效度：并行度用存活租约数 + 冲突率度量，需有效 merge 交叉校验。

增量贡献在组合——多独立 LLM 会话 + 无人工干预 + 目录级租约机器强制 + ECDSA 身份 + Shapley 贡献加权 merge；天然基线实验；租约上承 [Gray & Cheriton 1989](https://web.stanford.edu/class/archive/cs/cs240/cs240.1252/readings/cs240-annot-leases.pdf)。对比 [AgentNet](https://lacuna.tiptreesystems.com/paper/agentnet-decentralized-evolutionary-coordination-for-llm-based-multi-agent/art_ceff7e5ef97943ff96d0dd9731641d01)、[RAPS](https://arxiv.org/abs/2602.08009)。

## 结论

本报告回答了一个具体问题：多个独立 LLM 会话并行开发同一仓库，能否以协议而非中央编排器实现协同？答案是肯定的，且该方案可被初赛基线实验证伪。研究形成四点结论。

第一，问题本质是分布式并发控制与信用归因，而非 MARL 训练问题。CTDE 作为训练范式隐含「动作空间不重叠」的前提，套用于「写文件动作完全重叠」的代码协作必然互踩；本报告将其纠正为「部署期协作协议」。

第二，现有治理方向正确、机制名不副实。单写者全局互斥锁把 N 会话压成串行 1×，身份裸字符串可撞名冒充，贡献归因与拜占庭防御缺失。对照 Anthropic 多 agent 提升 90.2%（[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)）与 Cognition 的单写者主张（[Cognition](http://www.cognition.ai/blog/multi-agents-working)），本方案以「目录级多写者租约」在两者间取平衡，将写并行度由 1× 提升至 N×。

第三，协议全栈可实施：多租约映射、scope 相交判定、双时间戳租约与 fencing token 防迟到写、Ed25519 签名身份、双权重归因、门控隐式通信与完整状态机；拜占庭界按层级区分——结果层鲁棒聚合 f<n/2（[DecentLLMs](https://arxiv.org/abs/2507.14928)），租约层签名 fencing 无 f 界，未来异步共识 f<n/3（PBFT）。

第四，可发表性在于「组合增量」：多独立会话 + 无人工干预 + 目录级租约机器强制 + ECDSA 身份 + Shapley 加权 merge，并可对照初赛 62 题 0 解出的天然基线做 Wilcoxon 配对检验证伪。诚实局限同样明确：归因权依赖平台 accepted 数据、当前无法校准为绝对分；租约只解决「写不冲突」而非「写对不对」，仍需 Reviewer 门禁兜底。

下一步沿三条路径推进：以写耦合度聚类定租约粒度、引入难度系数修正归因权偏向、重开赛后以离线回归集落地五项指标验证。
