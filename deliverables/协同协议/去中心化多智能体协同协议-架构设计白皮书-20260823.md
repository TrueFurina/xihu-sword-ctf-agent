本白皮书回答一个问题：**一堆独立 LLM 会话，如何在同一份代码仓库上并行开发而不互踩、不撞名、不失忆、不空转？**

它与另两份文档的关系：

| 文档 | 回答 | 性质 |
|---|---|---|

| **《架构设计白皮书》（本文）** | **架构全貌**（分层 + 状态机 + 门禁 + 任务板） | 设计层 |
| 《工程落地规格》 | **怎么做**（接口签名 + 伪代码 + 测试 + 路线图） | 实现层 |

阅读路径：**方案报告定方向 → 白皮书看全貌 → 落地规格照写码**。

## 1. 架构总览：四层 + 一底座

去中心化多智能体协同 = **共享 git 工作树底座** 之上，自底向上的四层：

```
编排层（谁干什么）     声明式任务板 —— 反共识：不上全职 Orchestrator
门禁层（写对不对）     三道机器门禁 + Reviewer 验收 —— 密钥/诚实口径/租约 + 单点兜底
归因层（谁贡献什么）   写耦合聚类定 scope + 双权重（merge 权 ≠ 归因权）
租约层（写哪不冲突）   目录级多写者租约 + scope 相交 + 双时间戳 + fencing
身份层（谁在写）       唯一 ID + 登记绑定（可选 L3 ECDSA 签名）
─────────────────────────────────────────────────
底座                   共享 git 工作树 —— 唯一事实源（coordination.json / identity 表 / 任务总账）
```

**核心设计判断**：没有中央编排器，也没有会话间直连消息。会话之间唯一的同步通道是 **git 提交 + 三个数据文件**——这是 COCOM「隐式共识生成」的落地：每次 `git pull` 即获得全局视图，广播只在阻塞升级时发生（门控通信）。

---

## 2. 底座：共享 git 工作树（唯一事实源）

三个数据文件构成全部状态，git 是唯一共识载体（无服务器、无数据库、无消息队列）：

| 文件 | 内容 | 承载层 |
|---|---|---|
| `.atomcode/coordination.json` | 租约映射 + 身份表 | 身份层 + 租约层 |
| `tasks/` 目录（规划） | 声明式任务板 | 编排层 |
| 任务总账（`协同任务总账-TOP0.md` + post-commit 自动记账） | 归因流水 | 归因层 |

**为什么 git 是正确底座**：乐观并发（冲突即 rebase + retry，无需分布式锁）、天然审计（每次写入可追溯）、零基础设施。这对应 GNAP（git-native agent protocol）的哲学——「git 是唯一事实源，其余都是 application layer」。

---

## 3. 身份层：谁在写

**职责**：让每个写入者可验证，堵「撞名」和「冒充」。

三级递进（按威胁模型决定上到哪一级，不一步到位）：

| 级 | 机制 | 解决 | 状态 |
|---|---|---|---|
| L1 | 唯一 ID（`<name>-<8位hex>`，`_sign.py init_session`） | 撞名 | ✅ G2 落地 |
| L2 | 登记绑定（公钥指纹登记进 identity 表） | 会话↔身份对应 | ✅ G2 落地 |
| L3 | ECDSA 签名（每会话密钥签 commit，pre-commit 校验签名会话 == 租约会话） | 恶意冒充 | ⏳ G5 未落地 |

**关键判断（何时上 L3）**：L3 的威胁模型是「恶意冒充者」，而本项目当前是「会犯错的队友」。**在无恶意攻击者时，L1+L2 已足够，L3 是过度工程**。这也是 G5 被正确推迟的原因——它依赖「无人工干预的公开协同」这一前置，当前不成立。

---

## 4. 租约层：写哪不冲突

**职责**：把「N 个会话写同一仓库」从「串行排队」变成「不相交目录并行」。

四个机制（`scripts/_lease.py`，G1 落地）：

| 机制 | 解决 | 实现 |
|---|---|---|
| 多写者租约映射 | 单写者锁 → 多租约并行 | `coordination.json` 单 session → `{version, identity, leases}` |
| scope 相交判定 | 不相交 scope 可并行 | `scopes_conflict()`：glob 前缀展开 + 前缀包含判定 |
| 双时间戳 | 活跃心跳 ≠ 提交（防误杀长计算会话） | `last_active`（存活判定）/ `last_commit`（归因）分离 |
| fencing token | 过期节点迟到写（防抢锁后旧写者污染） | `key_id` + `lease_version`，pre-commit 校验版本单调递增 |

**这是全架构唯一已完整落地的核心层**——也是「多智能体协同」四个字成立与否的分水岭。它的理论锚点是 Gray & Cheriton 1989 租约（持锁者崩溃不死锁）+ Chubby 2006 fencing（迟到写拦截）。

---

## 5. 归因层：谁贡献什么

**职责**：把「谁写的」量化成「谁贡献了什么」。

两个正交机制，严格分离（避免不可靠权重污染可靠权重）：

| 机制 | 计算 | 用途 | 状态 |
|---|---|---|---|
| **写耦合聚类**（`_coupling_cluster.py`） | git 历史文件共现矩阵 → Jaccard → average-linkage 聚类 → scope 建议 | 定 scope 粒度（可发表点） | ✅ G4 落地 |
| **merge 权** | 验证通过的提交数 | 投票/合并决策 | ✅ 客观可算 |
| **归因权** | accepted 解出 × 难度系数 | 贡献排名 | ⏳ 待 accepted 数据（平台关，无法校准） |

**G4 的价值证明**：average-linkage 聚类后，输出从「一团 `/**`」变成真实的「代码 + 对应测试」耦合对（`scripts/_lease.py; tests/test_lease.py`）——这正是 scope 划分该有的产出，也是相对所有工业界「人工拍目录」的增量。

---

## 6. 门禁层：写对不对（含 Reviewer 门禁设计 · 增量）

**职责**：机器拦「形式上不对」，人拦「语义上不对」。

### 6.1 三道机器门禁（事前，pre-commit）

| 门禁 | 拦什么 | 实现 |
|---|---|---|
| ① 密钥扫描 | 凭据泄漏（ak_live_/sk-/token） | `_scan_secrets.py --cached` |
| ② 诚实口径 | 假水位（解出数递增 / 真实解出 flag） | `_honesty_scan.py --cached` |
| ③ 租约 | 越界写 / 无租约写 | `_lease.py precommit` |

机器门禁的共同特点：**二值（绿/红）、事前、可回归**。它们管的是「形式上必然错」的提交。

### 6.2 Reviewer 验收门禁（事后，merge 前 · 增量设计）

机器门禁解决「写不冲突」，**不解决「写对不对」**——假解出、错误逻辑、语义 bug 机器拦不住。这是 Reviewer 门禁的定位：**最后一道语义关**。

**设计（单点，非多点）**：

| 检查项 | 自动化？ | 说明 |
|---|---|---|
| pytest 全绿 | ✅ 自动 | 回归基线，机器可判 |
| diff 全在租约 scope 内 | ✅ 自动 | 复用 `_lease.py` 的 scope 校验 |
| 诚实口径 | ✅ 自动 | 复用 `_honesty_scan.py` |
| **语义正确性** | ❌ 人工 | 逻辑、正确性、假解出——机器管不了的部分 |

**为什么单点而不是多点**：多 reviewer 会引入协调成本（谁先审、意见冲突怎么办），这正是 Cognition「单写者 + 只读子 agent」反方主张的教训——**写保持单点收敛，只读并行**。Reviewer 是唯一 integrator，其余会话只读审查。

**触发时机**：任何 merge 回 `main` 前。代价是 merge 变串行，但 merge 本身就该串行（合并是紧耦合操作，不可并行）。

**现状**：三道机器门禁 ✅ 落地；Reviewer 验收门禁 ⏳ 未落地（当前靠协调者人工 ad hoc 裁决）。

## 7. 编排层：谁干什么（声明式任务板 · 增量设计）

**职责**：决定「谁干什么」，但不引入中央编排器。

**反共识判断（已定）**：**不上全职 LLM Orchestrator**。理由——CTF 是 embarrassingly parallel + 高度动态，全职 orchestrator 只会烧 token + 变单点瓶颈（Anthropic 的 15× token 成本中「编排者开销」是主因）。编排退化为「声明式任务板 + 一个薄脚本」。

### 7.1 任务板数据结构（tasks/ 目录，每任务一个文件）

```json
{
  "id": "task-crypto-01",
  "title": "CRYPTO-01 RSA 费马分解",
  "scope": ["data/crypto-01/**", "skills/rsa_fermat_factor.py"],
  "status": "in_progress",
  "claimed_by": "gu-crypto-3f2a",
  "claimed_at": "2026-08-23T10:00:00Z",
  "reviewer": "gu-integrator",
  "result": null
}
```

### 7.2 任务状态机

```
backlog → ready → claimed → in_progress → review → done
                     └→ blocked ──────────┘
                     └→ cancelled
```

### 7.3 认领协议（乐观并发，无锁）

两个会话同时认领同一任务时，**git 的 non-fast-forward 拒绝天然判定「后提交者失败」**，失败方 pull --rebase 后重读任务板再认领（最多 3 次）。这是 GNAP 的 task-claim-race 先例——**把认领竞态交给 git 的乐观并发，不引入分布式锁**。

### 7.4 为什么「声明式」而非「命令式」

声明式：任务板只声明「要做什么、谁认领了、什么状态」，session **自己看板认领**，无需中央调度器下发指令。命令式（orchestrator 派单）需要中央器实时掌握每个 session 状态——在去中心化场景既脆弱又昂贵。

**现状**：⏳ 未落地（当前靠「协同任务总账」人工维护 + 协调者 ad hoc 派单）。

## 8. 会话完整生命周期状态机（增量）

之前只设计了「租约」的状态机，缺「一个会话」跨越四层的完整生命周期。补全如下：

```
            ┌────────────────────────────────────────────┐
            │              冲突/越界：re-acquire 或等待      │
            │               ┌──────────────────────────┐  │
            ▼               ▼                          │  │
init → claim → acquire → work ⇄ heartbeat → commit → review → merge → closeout
│        │        │        │                  │        │       │
│        │        │        └── 租约层 ────────┘        │       │
│        │        └── 租约层 + 身份层                    │       │
│        └── 编排层（任务板）                            │       │
└── 身份层（唯一 ID 生成）                               └── 门禁层（Reviewer）
```

各状态的触发条件与动作：

| 状态 | 触发 | 动作 | 涉及层 |
|---|---|---|---|
| `init` | 会话启动 | 生成唯一 ID + 登记 identity 表 | 身份层 |
| `claim` | 看任务板 | 认领一个任务（git 提交，乐观并发） | 编排层 |
| `acquire` | 认领后 | 对 scope 发起 acquire，相交判定 | 租约层 |
| `work` | 获取租约 | 在 scope 内读写，周期 heartbeat 续租 | 租约层 |
| `commit` | 完成一轮工作 | pre-commit 三门禁 → 提交 | 门禁层（机器） |
| `review` | 提交后 | pytest 全绿 + scope 内 + 语义终审 | 门禁层（Reviewer） |
| `merge` | 验收通过 | 合并回 main + release 租约 | 门禁层 + 租约层 |
| `closeout` | 会话收尾 | `_closeout.py` 检查在飞改动清零 + 工作树 clean | 治理 |

**关键设计**：`work` 是唯一可并行的状态（多个会话同时 work，只要 scope 不相交）；`commit` 之后的所有状态天然收敛（merge/review 是紧耦合操作，串行）。这精确呼应了 Cognition 的「写单线程、读并行」——**读（work 中的 pull/分析）并行，写（commit/merge）串行**。

## 9. 已落地 vs 未落地诚实对照

> **状态以机器事实源 [`FACTS.md`](FACTS.md) 为准**——租约模式、G0-G4 落地、门禁状态、HEAD 由 `scripts/_facts.py --write` 从代码与 git 实时采集，本表是其快照；漂移时以 FACTS 为准（根治「手写状态断言漂移」，不再各自维护一份手写断言）。

| 层 / 机制 | 状态 | 落地物 |
|---|---|---|
| 底座 git 工作树 | ✅ 已落地 | coordination.json + post-commit 记账 |
| 身份 L1+L2 | ✅ 已落地 | `_sign.py`（G2） |
| 租约多写者 | ✅ 已落地 | `_lease.py`（G1） |
| 收尾脚本 | ✅ 已落地 | `_closeout.py`（G3） |
| 写耦合聚类 | ✅ 已落地 | `_coupling_cluster.py`（G4） |
| 三道机器门禁 | ✅ 已落地 | pre-commit（密钥/诚实口径/租约/身份绑定 ④ 道） |
| git 身份绑定（P1-7） | ✅ 已落地 | `_sign.py bind`（T-11） |
| Reviewer 验收门禁 | ✅ 已落地 | `_reviewer_gate.py`（T-10，机器三查 + 人工终审） |
| 声明式任务板 | ✅ 已落地 | `_task_board.py`（T-09） |
| 身份 L3 ECDSA | ⏳ 未落地 | 依赖「恶意冒充威胁」前置 |
| 归因权（accepted × 难度） | ⏳ 未落地 | 依赖平台 accepted 数据 |

**一句话现状**：**「不互踩」（身份 + 租约 + 门禁）已完整落地，「不空转」（任务板）已落地，「写对不对」（Reviewer 机器三查已落地、语义终审留人工单点）；唯一未落地的是依赖外部前置的「归因权」与「身份 L3」——正确地等待前置，而非为了做而做。**

## 10. 设计决策与理论锚点映射

| 设计决策 | 理论锚点 | 来源 |
|---|---|---|
| 租约多写者 + fencing | 租约（持锁者崩溃不死锁）+ Chubby sequencer | Gray & Cheriton 1989; Burrows 2006 |
| scope 相交判定 | 资源分区（吞吐 N× vs 互斥 1×） | 分布式系统 |
| 写耦合聚类定 scope | 逻辑耦合（共现 = 演进耦合） | Gall et al. 1998 |
| git 乐观并发认领 | task-claim-race | GNAP |
| 隐式共识（git 同步） | 隐式共识生成 + 门控通信 | COCOM, AAAI 2025 |
| 不上全职 Orchestrator | 编排器 = 成本中心 | Cognition 反方; Stanford DeLM |
| 双权重归因 | Shapley 四公理（O(2^n) 需近似） | Rozemberczki 2022 |
| 诚实口径机器门禁 | 机器强制 > 自觉 | 项目纲领 §1 |

## 11. 演进路线（G5 及以后）

按「依赖前置满足」排序，不「为了做而做」：

1. **声明式任务板**（编排层落地）——前置：无。价值：终结「协调者人工派单」。
2. **Reviewer 验收门禁**（门禁层补全）——前置：任务板。价值：终结「语义正确性靠人工 ad hoc」。
3. **归因权校准**——前置：平台重开、有 accepted 数据。价值：贡献可量化。
4. **身份 L3 ECDSA**——前置：出现恶意冒充动机。价值：密码学防伪。

**诚实结论**：1、2 现在就能做且该做（它们终结的是「人工 ad hoc」，不是「为了炫技」）；3、4 正确地等待前置，做了也无法验证 = 重演 RDD。
