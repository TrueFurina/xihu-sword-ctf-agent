## 〇、一句话结论

这份协议写了**三层好意图**（开工登记、文件隔离、门禁是神），但执法层只实现了其中一层的一半——**租约管了"谁写哪"，没管"红不红、是不是越权、有没有登记"**。协议里最能打的三条硬规则，有两条是纸面的。

**根本病灶**：规范层在写诗，执法层在裸奔——规则与执法层之间存在系统性落差。机器只拦"谁写哪"（租约 scope），协议却宣称拦了"红不红、登不登记、越不越权"——后面三样全是自觉。

## 一、P0 —— 结构性致命（不修 = 事故重演）

### P0-1. 「门禁是神」是假神——pre-commit 根本不跑 pytest
- **位置**：R3（第 57-60 行）vs `scripts/hooks/pre-commit` / `git_hooks/pre-commit`
- **实测**：两个 pre-commit 里 `grep pytest` = **0 处**。门禁只有三门：密钥扫描、假水位扫描、租约。
- **锐评**：协议说"任何代码改动后 pytest 必须绿""全量门禁说了算"——但执法层从头到尾**没有把 pytest 放进机器门禁**。这解释了为什么 `1d91f68`（"解出数 16→26 实证"）能在测试全红时提交成功：不是会话故意违规，是**协议给了它一个不存在的"门禁"**。带红提交是结构性可重复发生的，因为结构里没有那道闸。
- **建议**：要么把 `pytest -m "not slow"` 加进 pre-commit（慢就拆慢速门禁/CI），要么协议如实写"pytest 绿是自觉条款，机器不拦"。**现在这样写，是把自觉包装成机器执法——和假水位文档是同一个病**。

### P0-2. 「单写者全局租约」的"诚实说明"是过时谎言
- **位置**：第 15-16 行
- **实测**：`_lease.py:118` 已实现 `scopes_conflict`（scope 相交判定），`:164` 按"scope 不相交即可并行 acquire"放行。**当前实时存在 4 个并存租约**：gu(data/results)、reviewerA(agents/**)、reviewerB(skills/**)、closeout(core+scripts+tests+tools+git_hooks)。
- **锐评**：协议白纸黑字写"当前执法层实现为**单写者全局租约（同一时刻仅一个会话可写）**，目录级多写者是规划中的 G1 尚未落地"——**实测 G1 已经落地了**（4 个会话并行持租约在跑）。协议一边自称"诚实说明"，一边与代码差了一个版本。**"诚实说明"都不诚实，这份协议还有什么资格要求别的文档诚实？**
- **建议**：更新为实测口径（scopes_conflict 已生效、多写者并行已存在）。

### P0-3. R3.3 教唆 `git checkout -- <文件>`——这是销毁别人工作的命令
- **位置**：第 60 行"先 `git checkout -- <文件>` 恢复"
- **实测**：并行会话正在飞 **15 项未提交改动**（core/main_agent.py、presolve.py 等）。`git checkout -- <文件>` 会**无条件丢弃工作区未提交改动，不可恢复**。
- **锐评**：这份协议教每个会话"测试红了 → 先 checkout 恢复"——**执行一次就可能把另一个会话几个小时的成果抹掉**。协议自己开篇说"并发不可怕，无锁并发才可怕"，然后教大家用一把会随机抹掉别人工作的刀。这是把"恢复"包装成"修复"。测试红的第一动作应该是 `git status` 看**谁**改了，正确的下一步是**协调者仲裁**，不是无条件 checkout。
- **建议**：删除该命令，改为"git status 定位改动归属 → 协调者裁决 → 定向处理"。

## 二、P1 —— 功能/可维护性（纸面规则 vs 真实行为）

### P1-1. 双锁体系并存，没有一个人能说清该信谁
- **位置**：R1（第 47-50 行 `.workbuddy/locks/<文件>.lock`）vs 执法层（`_lease.py`）
- **实测**：`.workbuddy/locks/` 目录存在，但 pre-commit 只检查 `_lease.py` 租约，**完全不读 .lock**。
- **锐评**：协议里有两套锁：一套机器执法（lease，commit 时拦）、一套自觉登记（.lock 文件，无任何执法）。会话 A 建了 .lock 以为锁住了，会话 B 不认 .lock 照样 acquire 租约写文件——**两个锁系统互不知道对方存在**。这比没锁更危险：给所有人一种"我被保护了"的错觉。
- **建议**：宣布 .lock 机制**废弃**（或降级为"工作区可见登记"辅助层），唯一执法入口 = `_lease.py`。

### P1-2. 「核心文件只读」没有任何执法手段
- **位置**：R2（第 54 行：run.py/config.py/core//ctfplatform/ 对非协调者只读）
- **实测**：main 历史上 `0dcf348`(core/presolve)、`4b95160`(core/presolve)、`2528452`(核心)、`5f4ebd4`(_coupling_cluster) 全是**非协调者在动核心文件**——且都提交成功。lease 只认 scope 路径，不认"角色权限"。
- **锐评**："核心文件全域只读"是一句**没有警察的法律**。会话只要 acquire 了覆盖 core/** 的租约（比如 closeout 那个全域租约），照样改核心。协议的角色表写了"协调者唯一可动"，但**没有任何机制把"唯一"变成现实**。
- **建议**：要么在 `_lease.py` 里加角色-路径黑名单，要么协议承认"只读区是君子协定"。

### P1-3. TASK_BOARD 是装饰品——任务总账 8/23 无一条登记
- **位置**：第三章（第 71-87 行）
- **实测**：任务板 T-02~T-05 全标"🔄 进行中"，但 main 上 8/23 的 commit（1d91f68 假水位、99fb169 flag 明文、0dcf348/4b95160 核心改动）**全部没有对应任务登记**；核查发现"任务总账无 8/23 登记"。
- **锐评**：R1 说"开工必登记"——**从登记第一句开始就没人遵守**。任务板停在 8/22 的快照，8/23 所有真实工作都在板外进行。协议把"登记"写成硬规则（"违反 = 重演 0 分"），但违规行为没有任何后果（commit 照常过门禁）。**规则的威慑力 = 0，因为执行 = 0**。
- **建议**：commit 模板强制关联任务 id，或 pre-commit 检查任务板登记。

### P1-4. 快照「208 passed 终态基线」与实际差 20 个测试
- **位置**：第 27 行
- **实测**：当前全量 = **228 passed / 6 skipped / 2 deselected**；且 8/23 出现过 222+1 FAILED 红态。
- **锐评**：快照写"208 passed / 1 skipped（终态基线）"——**终态基线**四个字尤其刺眼：8/23 全天测试数在 208→222→228 之间波动，哪来的"终态"？接手续航的会话拿 208 当基线，第一眼就会误判"测试少了/多了"。
- **建议**：快照必须标注采集时间 + 每次改协议重跑全量。

## 五、最终裁定

这份协议**方向是对的、语气是真诚的，但它描述的是"应该存在的世界"，不是"存在的世界"**。最致命的不是哪一条规则写得差，而是**规则与执法层之间存在系统性落差**：机器只拦"谁写哪"（租约 scope），协议却宣称拦了"红不红、登不登记、越不越权"——后面三样全是自觉。**自觉在单会话时代够用，在多会话并发时代就是事故源**（`1d91f68` 带红提交、`99fb169` flag 明文就是证据）。

下一版协议只需要做一件事就够：**把"自觉条款"和"机器执法"分开列，自觉的别叫"硬规则"，执法的别只做样子**。

### P1-6. 「单写者全局租约」是**三方同步谎言**（协议 + AGENTS.md + 规格文档）
- **位置**：协议第 15-16 行、`ctf_agent/AGENTS.md` 第 10 行、`deliverables/协同协议/多智能体协同协议-工程落地规格-20260823.md` 第 6/14/30 行

### P1-7. git 身份与会话租约身份**完全脱钩**——职责表在 git 层面不可执行
- **位置**：协议角色表（第 36-39 行「协调者唯一可动 main」）
- **实测**：main 近 15 个 commit **全部 author =「糖露星霜•暖霞拾光」**（唯一），无法区分是哪次会话提交；租约持有者（gu / reviewerA / reviewerB / closeout）与 git author **无任何映射关系**。
- **锐评**：协议规定「协调者唯一可动 main 分支」，但 git 层**根本无法验证**「这个提交是协调者还是执行会话发的」——任何会话都能以协调者身份提交。**职责表在 git 层面既不可执行，也不可审计**。P1-2（核心只读无执法）的根因就在这里：连"谁提交的"都分不清。
- **建议**：git author 与租约 session 绑定（如 commit 模板强制带 session 标识），或至少按 commit 内容人工归因。

### P1-8. 快照「当前分支 main 远端 1c3dc15」**再次过时**
- **位置**：协议第 30 行
- **实测**：实际 HEAD = `489e4e6`（8/23 又推了多个 commit，含 871cc02 等），远端早已前进。
- **锐评**：快照是协议最重要的"接续真相"，但 8/23 白天就过期了。**快照不更新的协议 = 只写了"当前状态"四个字**。第一轮 P1-4 已批快照数字失真，这一条连 commit 哈希都对不上——快照机制整体失效。
- **建议**：每次协议更新时同步重跑 `git rev-parse HEAD` + `pytest`，把两个值写进快照。

### P2-4. 快照数字 208/164 **无任何提交可溯源**
- **位置**：协议第 27 行「164@09:35 → 208@8/22 DoD」
- **实测**：git log 全历史中**无任何提交**提及 208 / 基线 / DoD 的出处，数字无法从 git 历史验证。
- **锐评**：无溯源的数字 = 无证据的数字。与假水位文档同病：**声称"208 终态基线"却拿不出产生 208 的那次运行**。数字本身可能没错，但"怎么来的"必须可查。
- **建议**：数字后附 pytest 输出文件路径或 commit 哈希。

## 六·五、第六轮锐评全文存档（2026-08-24 收录）

> **来源**：外部锐评方《西湖论剑 CTF-Agent 第六轮锐评》（标准：真实解出数 / 第一名 / 最短时间）。

### 锐评原文（节选完整）

**一、先发奖牌：这轮的诚实基建是真材实料**

- 测试 278 passed, 0 failed，快速回归集扩到 73 用例，比赛墙钟挂进 benchmark（max duration 59.5s < 300s，上轮的失真死了）。
- 监督采纳率统计上线（d773869）——上轮要求"没有采纳率的监督者无法自证不是摆设"，这轮直接给了裁决流水 + 5 个单测。这是六轮里点名的问题被回答得最干脆的一次。
- RSA 映射：没有改五行映射，而是加了根因注释——文件名是历史包袱，真实分发靠 crypto_auto 的 auto-detect 链（费马/小指数/Wiener/共模/Hastad 自动轮试）。这是合理的工程判断：改名会破坏实证链，注释 + 自动链比硬改映射更对。接受。
- 诚实水位声明文档本身，结构已是世界级：三条水位线、37/49 的构成拆解、熔断风险主动披露（"baidu 长跑触发 403，reverse-005 被跳过——37% 可能低估但当前无法验证"）、甚至写进了"任何人汇报 75.5%，第一反应追问 presolve 命不中的 19 题解出几道"。这份文档对自己的怀疑，比对任何人都狠。这是好东西。

**二、然后是刀：web 0/10 → 10/10，是六轮以来最漂亮的一次循环论证**

1. 题目是自产的：web-001~010 是你们自己写的简化教学题（"西湖论剑 sqli or not 简化"），flag 是自己定的。
2. 靶机是自建的：340 行，端点是"最小漏洞端点"——"payload 特征命中即返回 flag（模拟漏洞利用成功，不真实执行）"（源码第 14 行原话）。它不执行注入、不求值模板、不反序列化——它做的是正则匹配你们探测器的 payload 长什么样。{{7*7}} 出现就算命中，O:5: 出现就算打穿。
3. 探测器是照着靶机写的：_try_web_probe payload 表驱动，特征对着这十个端点调。

出题人、靶机、考生是同一个人。这 10/10 测出的是"探测器和靶机的接口对上了"——是管道测试通过，不是解题能力。它对真实赛场 web 题的预测力是零：真实靶机不会用正则奖励 payload 特征，会用真实的 WAF、真实的过滤、真实的多步逻辑打你的脸。

更要命的是这对 KPI 的污染。你们昨天刚立法："唯一 KPI = 客场全量 37/49 往上爬"。24 小时内 KPI 涨了 10 分——路径不是"Agent 变强了"，而是"给 10 道题配了会认输的靶机"。这是古德哈特定律的教科书案例：当一个指标成为唯一目标，最快提升它的方法一定是造指标，而不是造能力。37/49 里现在有 10 分是自产自销的。

还有一记回旋镖：真正的客场数字——60 道真题的 5/60 = 8%——被"已被本版取代"一句话退役了。取代它的 49 题（data/questions）是你们自己的题库。也就是说："客场"这个词现在指向的是主场。74% → 91.7% → 16→26 → 86.7% → 75.5%，这是同一首歌的第五个 remix——但这次连"客场"的词义都被借走了。

**三、公道话：web 靶机这件事，方向是对的，罪在记账**

自建靶场是正经的评测基建——就像给 Agent 造了个健身房。问题只有两个：

1. 健身房不能记成绩单。web 10/10 应该记为"评测环境就绪"，计入 0 分。真实成绩单上，web 一栏应该写："未知——真题 web 题从未在真实靶机上验证过，0 实证"。
2. 靶机的"漏洞"是正则不是漏洞。要让健身房真练出肌肉，靶机必须真的执行：SQL 真查库、SSTI 真渲染、反序列化真 pop。否则 LLM 学到的"这样发 payload 就有 flag"是假规律，上了赛场会被真实响应格式直接打懵——训练环境的仁慈，就是赛场的残忍。

**四、KPI 已经被污染，怎么救**

两步：
1. 把 web-001~010 从 KPI 分母里摘出去（或单独标注"自建靶场 10/10，不计入客场"）。KPI 回到 27/39 或直接改成分层记账：真题解出数（唯一 KPI）/ 教学题解出数 / 靶场管道测试（不计分）。一个数字一旦被造过假，只有更严的口径能救回来。
2. 把 5/60 的真题集请回来当主考官。它才是唯一有预测力的考场。今天所有的 presolve 新模板（web_probe、垃圾 flag 过滤、第七路审计），都应该拿到 60 道真题上重跑一遍——涨没涨，那边说了算。你们 8 月份吃过的最大的亏，就是拿自家题库当考场。

**五、还有一个小刺：熔断让 KPI 不可复现**

水位文档自己披露了：长跑中 baidu 熔断，reverse-005 被跳过。这意味着 37/49（以及 7/19）这个数依赖当时 provider 的脸色——额度没烧完是 37，烧完是 35，谁也说不好。你们给了竞速池配熔断和 12 路 provider，却让唯一的 KPI 测量跑在单 provider 上。测量系统的可用性应该高于被测系统——benchmark 至少双 provider 互备，否则每次跑出来的数都不可比，趋势就断了。KPI 的价值全在"可比"，不可比的 KPI 等于没有。

**总判决**

诚实基建：A-（文档结构、熔断披露、采纳率统计，都是真进步）。KPI 纪律：F（自建靶场 10 分计入客场 KPI + 退役真题考场——这轮最大的失分，而且是以最专业的姿态犯的）。

六轮下来，这个项目呈现出一个惊人的模式：你们的治理、文档、测试、复盘能力一直在 A 级水平，而且一轮比一轮强；但每次能力逼近诚实的边缘，就有一股聪明的力量把考场搬回主场。第一轮是抄答案，第二轮是复盘口径，第三轮是 n=1，第四轮是 16→26，这一轮是自建靶场。手法越来越精巧，性质一次没变：用最好看的数字，替代最难受的数字。

决赛倒计时阶段，最后三条军令：

1. 今晚：KPI 摘除自建 web 10 题，恢复 5/60 真题集为唯一 KPI 考场，水位声明改口径。这是把第五次自欺掐死在 24 小时内的最后机会。
2. 靶场留用但不计分，并把靶机从"正则认输"升级为"真实执行"——决赛前能升多少升多少，它是唯一安全的 web 训练场。
3. 所有人所有时间砸向 19 题（presolve 命不中的那批）+ 真题 55 题的第一堆——每题一个 commit、一个真 flag、解不出如实记"不变"。你们已经会做这件事了，缺的只是只对着真题做这件事。

最后一句话：你们的 Agent 已经不怕难题了——怕难题的是你们自己。每次把考场搬回主场，都是在告诉团队"我们赢不了客场"。而客场才是比赛举办的地方。去把 5/60 的 5 变成 10，那才是第一名路线上的第一个真实台阶。
