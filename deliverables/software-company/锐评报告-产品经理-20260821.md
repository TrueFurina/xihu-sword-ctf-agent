## 二、数据复盘结论（正式赛 0/62 的六层根因 + 教训）

### 2.1 题型解出率分布（正式赛实战 vs 本地）

| 题型 | 本地真解出 | 正式赛 32 题分布 | 正式赛解出 | 结论 |
|------|-----------|-----------------|-----------|------|
| crypto | 9/10（基本盘） | ~7 | 0 | 正式赛真题是 PKCS#1 v1.5 / e=65536 类，本地 skill 全是 RSA 小 e/费马/Wiener——**能力错配** |
| misc | 7/10（稳） | 被误判 75%（24/32） | 0 | 分类器靠 title 猜测，大量动态题被当静态题空转 |
| pwn | 3/5 | ~7 | 0 | 有附件却靠猜 flag（幻觉），确定性链兜底缺失 |
| reverse | 2/5（弱项） | ~9 | 0 | 大文件（exe/apk）分析慢，工具链弱 |
| web | 0/10（本地无靶机=预期 0） | ~7 | 0 | 靶机 HTTP/HTTPS 000 连接失败，交互未打通 |

**锐评**：本地 52 题题库 = 自出题 + 测试赛同源 corpus + 历史真题，**72% 是自出题幻觉**；正式赛 32 题 = 全新真题。**本地语料与真实赛题的相关性≈0，这是"92%→0%"结构性塌方的根源。**

### 2.2 耗时瓶颈

| 瓶颈 | 数据 | 锐评 |
|------|------|------|
| 同一题反复空转 | 平均 8.4 次/题，最高 12 次，13 题被尝试 12 次 | 墙钟止损只是"放弃本题换下一题"，但下一题同样缺数据——**止损止错了对象** |
| LLM 空转吞噬墙钟 | 87.2% 记录是纯 `recon:reason`，仅 8.4% 调用工具 | Agent 无数据时不下载/不探测，而是反复"思考"，被空 Question 逼入死循环 |
| 确定性链拖死并发池 | rsa_chain 对 zip 附件 600s 卡死 | 已修复（跳过二进制附件→0.0s），但暴露**性能 bug 无赛前压测** |

| HARD 题无确定性解 | specialcurve2 487s stuck_loop，靠操作员手动 | 符合"不赌模型"定位，但要写进答辩口径 |

### 2.4 赛时管理教训（产品视角 5 条）

1. **赛前 4 小时仍在动代码**：产品评估 09:51 给 GO 时已列 P0-1 冻结纪律，但 11:47-13:19 仍在加 skill、改核心文件——冻结纪律被"再优化一次"的心态击穿。
2. **多 AI 会话无锁并发写坏核心文件**：11:10 实测 `run.py` SyntaxError（`if use_mock:/n` 字面量换行），HEAD 都有正确版本却没人 checkout。**协作失控 > 技术缺陷**。
3. **诊断=修复、写进文件=生效，两个等号都不成立**：14:47 已诊断根因、代码也写了修复，但活进程没重启加载 → 白改。这是全场最痛的教训。
4. **provider 口径漂移**：环境变量=deepseek vs 文档=主力 qwen 打架，赛前未定音，最终全源尽灭时无预案可切。
5. **记账源被污染**：goal_log 1504 行训练噪音（含 `flag{got_it_2026}` 占位符），若赛中靠它判断进度必然误判——还好最终只信了平台 accepted，否则连"0 解出"都会被误报成"解出 2 题"。
