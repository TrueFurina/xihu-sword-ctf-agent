## 一、架构评审

### 1.1 "1 主 1 监"设计是否落地有效

**落地：是。有效：存疑。**

- 主 Agent（`core/main_agent.py`，Plan-Act-Observe）+ 监督 Agent（`core/supervisor_agent.py`）结构清晰，依赖注入（registry/sandbox/checker/supervisor/coordinator）设计正确，`core/phases.py` 的职责拆分（plan/act/observe/supervise/extract_flag 五阶段外置）是可维护性的加分项。
- 监督 Agent 的**确定性规则优先**（`supervisor_agent.py:63-127`：工具失败≥2 换策略、同动作重复≥3 判死循环、连续失败升级、步数超限放弃）是全场最稳的设计——0 token、可预期。
- **但**：监督裁决与主循环内置护栏严重重叠。`main_agent.py` 的 solve() 单函数内堆了 10+ 条特殊护栏（墙钟、人工干预轮询、同参死循环、web 无靶机空转、全题型 reason 空转、crypto/misc 无数据止损、pwn/reverse 快速失败、高难首步重型、分级墙钟……），监督 Agent 的规则 2/3 与主循环的死循环检测**重复实现且阈值不同**（主循环 3 步相同 vs 监督 3 步相同），两套逻辑并行，行为靠注释记忆。**监督 Agent 的战略价值被主循环的"内联补丁"架空了一半**——真正的"换思路"决策实际由主循环里的 if 链承担。

### 1.2 确定性预扫（flag_scan/crypto_auto）与 LLM 推理路径的冲突/重复

**这是本次评审最重的架构发现：确定性解出路径存在 5 处重复实现，且无统一编排。**

| # | 路径 | 位置 | 触发条件 |
|---|---|---|---|
| 1 | fast_solve 关键词预检 | `run.py:182-233` | 题型 crypto/misc + 描述含关键词（凯撒/base64/morse/共模/小指数…） |
| 2 | 数学引擎矩阵 | `run.py:376-411` → `agents/math_engine.py` | 所有 race 题先跑（30s 名义超时） |
| 3 | 主 Agent 入口预扫 | `main_agent.py:191-215` | attachments 非空（flag_scan → crypto_auto） |
| 4 | 主 Agent 死循环兜底 | `main_agent.py:316-334` | 连续 3 步同参数 |
| 5 | phases.act_step 兜底 | `core/phases.py:135-218` | 附件分析完 + action∈(reason/flag/script)，crypto/reverse/misc/web 各自 fallback |

同一附件可能被嗅探 **5 次**（fast_solve 一次、math_engine 一次、入口预扫一次、死循环兜底一次、act_step 一次），每次都构造脚本 + 子进程执行，最坏把"秒解题"拖成"几十秒重复嗅探"。更危险的是**各路径成功判定口径不一**：run.py fast_solve 需过本地答案校验；math_engine 需过 is_correct；主 Agent 预扫只做正则提取，**不校验**——预扫命中 `ctx.candidate_flag` 后直接 break 返回，`_finalize` 会给 `confidence=0.9`（`main_agent.py:517` 硬编码），最终正确性由 FeedbackLoop 的 is_correct 兜底。若本地答案表为空（平台模式 validate_locally=False），预扫"格式合法即胜利"，可能把模板串当真。

### 1.3 过度设计 / 欠设计

**过度设计（over-engineering）：**
- `scheduler/rate_limiter.py`（令牌桶+熔断+备用切换）与 `scheduler/model_router.py`（三档路由）**在生产链路零引用**——grep 确认只有 scripts/ 和 tests/ 引用。v2.0 文档宣称的"分级降级调度/限流/熔断"实际由 `llm/client.py` 的 BoundedSemaphore + `_PROVIDER_CIRCUITS` 承担。**两套实现并存、文档讲一套、生产跑另一套**，决赛答辩若照文档讲会被评委追问。
- `core/goal_directive.py` 的 GoalLogger / self_reflection / skill_require 扩展字段：`_finalize` 里 `"supervision": VERDICT_CONTINUE` 恒为常量（`main_agent.py:527`），self_reflection 由规则自动生成而非模型输出，skill_require 的 `need_download` 永远没人真正下载（SkillManager 只从本地仓库加载）——**三个"亮点字段"目前都是写日志用的装饰**。

**欠设计（under-engineering）：**
- **端到端验证缺失**是最大欠设计：正式赛 0 解出的三个直接死因（附件永不下载、靶机永不注入、provider 全熔断）全部是"链路集成"问题，而 51 个测试全是组件级。没有一条"mock 平台 → 真附件 → 预扫命中 → 提交 accepted"的集成测试或彩排脚本。
- 主 Agent 的"护栏"全部是**事后打补丁**（每个护栏都对应一次实战翻车），没有抽象成统一的"止损策略"状态机——维护者无法回答"某道题走了哪条止损路径"。

### 1.4 模块边界

- 边界总体清晰：core（循环）/agents（领域工具）/skills（攻击脚本）/verify（校验）/sandbox（执行）/tools（适配器）/scheduler（调度）/ctfplatform（平台）/llm（客户端）/web（看板）。
- 越界点：`run.py` 是 798 行的"上帝入口"，同时承担 solver 组装、fast_solve 预检、race 编排、平台 solver、报告生成——`run.py:182-233` 的 fast_solve 预检与 `agents/crypto_toolkit.py` 的 fast_solve 强耦合；`main_agent.py:589-611` 的 5 个 `_build_*_fallback_script` 薄委托是好做法，但触发时机散落在 phases.py 各处。
- `ctfplatform/poller.py` 从 dasctf 客户端直接读 `platform._detail_cache`（`poller.py:269`），**破坏封装**——跨层访问私有属性。

### P0-2 竞速墙钟超时后后台任务泄漏（额度/资源黑洞）
- **位置**：`run.py:493-502`（`asyncio.wait_for(_race_with_wallclock(), timeout=_race_wc)`）+ `run.py:432-435`（`asyncio.create_task` 创建 in-flight solver tasks）+ `llm/client.py:494`（同步 `httpx.post`，不可被取消）+ `sandbox/subprocess_executor.py:255-265`（仅 `asyncio.TimeoutError` 杀进程，**CancelledError 不杀**）。
- **问题**：墙钟超时只取消外层 `_race_with_wallclock` 协程，**不会取消其内部已创建的 solver task**；task 里的同步 httpx.post 更无法被取消（要等网络 read 超时 60-300s 才返回）；子进程在 communicate 被取消时不会被 kill。后果：300s 墙钟到点后，12 路 solver 继续在后台空转烧 API 额度、挂子进程——正式赛 deepseek 402 前"数小时空转"正是此类资源黑洞的表现形式。
- **修复**：① `_race_with_wallclock` 用 `try/finally`，超时/取消时对 `pending` 全部 `task.cancel()` + `await asyncio.gather(*pending, return_exceptions=True)`；② `subprocess_executor.run` 捕获 `asyncio.CancelledError` 时同样 `_kill(proc)`；③ LLM 调用改为 `await asyncio.to_thread(...)` 或对每请求设置独立的真正可取消机制（至少在 race 场景用 `asyncio.timeout` 包裹并放弃结果，但必须保证子进程被杀）。

- **位置**：`main_agent.py:191-215`（入口预扫，要求 `attachments` 非空）→ 正式赛附件下载 bug 导致 attachments 恒为空 → 预扫永不执行；`logs/` 无任何 `[rsa_phi_known]/[rsa_hastad]` 命中记录；goal_log 仅测试残留。

- **修复**：① 修完附件下载后，必须做一次**真实平台端到端演练**：拉真题→附件落地→入口预扫命中→输出带 `[prescan:flag_scan]`/`[prescan:crypto_auto]` 日志标记；② 预扫路径加显式日志（当前只有 `logger.info("[%s] 确定性预扫命中")`，但 logs 里无记录——需确认在真实模式被调用）；③ 把"预扫命中率"纳入决赛看板指标，答辩可展示真实链路证据。

### P0-4 平台 429 风暴下 poller 把失败题永久标记 processed，且无限重试打爆限流
- **位置**：`ctfplatform/poller.py:137`（`self._processed.add(ch.id)` 在处理**前**加入）+ `poller.py:218-254`（get_challenge 失败→description/attachment 为空→"无解题数据跳过"）+ `ctfplatform/dasctf.py:123-161`（`_request` 重试 5 次指数退避最多 ~62s/次）+ `run_forever` 无 429 退避门控。
- **问题**：正式赛 3h 反复打爆 429（race.log 实测）。① 瞬时 429 导致某题详情拉取失败→被标记 processed→**整场不再重试该题**（丢题）；② 轮询每 30s 硬拉 list_challenges，429 时 dasctf 内部退避 62s，轮询节奏被拖垮；③ "拉取到 0 道题"后仍继续轮询，无退避。
- **修复**：① 失败的题不加入 `_processed`，或加入"待重试队列"（延迟 2-5 分钟再试，最多 3 次）；② poller 检测到连续 N 次 429 时轮询间隔指数退避（30s→60s→120s→300s）；③ `_request` 的 429 退避上限从 ~62s 降为 ~15s（429 是限流，快速失败让 poller 层面统一控制节奏）。

## 七、健壮性专项

- **LLM 超时/重试/熔断**：✅ 完整（connect 10s / read 60-300s / 400 降级重试 / 401/402/403 熔断 / 429 不熔断只让路 / 线程信号量 ≤8）。

## 十、架构亮点与风险

### 亮点（3-5）
1. **双矩阵异构竞速是真创新**：不是 12 个 LLM 内卷，而是"确定性数学引擎矩阵（第 0 号选手）"与"LLM 矩阵"并行，8/9 由确定性引擎零成本解出——架构立意高于普通多模型竞速。
2. **防幻觉/防烧钱护栏是全场最扎实**：三态 flag 校验 + 工具前置证据链 + 死循环检测 + 分级墙钟 + 三级预算 + 提交熔断，多层护栏形成一个完整的"诚实解出"闭环。
3. **LLM 客户端工程化到位**：白名单 fail-closed、401/402/403 熔断、400 降级重试、真实 token 记账、线程信号量——单模块质量可作答辩素材。
4. **平台层审计完备**：实例槽位准入（≤3）、提交串行锁、跨会话进度锁、本地落盘兜底、报告与流量日志吻合——"可追溯"是评委认可点。
5. **工程伦理在线**：DLP 独立性声明、answer_disclosed 去作弊护栏、赛后 0 解出诚实复盘——这份诚实本身就是决赛答辩的差异化优势。

### 风险（3-5）
1. **补丁堆叠失控**：main_agent.solve 一个函数 10+ 条护栏，互相纠缠，改一发动全身，组合场景无测试。
2. **确定性路径重复**：5 处嗅探实现并存，无统一编排，命中判定口径不一（最坏重复嗅探 5 次/题）。
3. **端到端验证缺失**：组件全绿、系统 0 解出——"集成"是最大风险面，且没有集成测试/彩排机制防止复发。
4. **并发模型混乱**：同步 httpx 阻塞事件循环 + 墙钟无法真正取消 + 全局 usage 记账失真——"看似并发实则串行+泄漏"。
5. **配置漂移**：provider 默认值三处横跳、注册表残留影响运行时、注释与代码矛盾——决赛前必须单一事实源。
