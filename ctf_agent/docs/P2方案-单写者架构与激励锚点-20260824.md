# P2 方案：单写者+多读者架构与激励结构物理锚点（2026-08-24）

> 本文档是评分反馈 P2 部分的**方案深化**（输出文档，不写核心代码）。
> 承接阶段 1-6 物理治理（worktree 车道 / 合并闸门 / 派生看板 / 一屏三铁律）。
> 核心立场：**治理已从宣言降到物理，P2 把「协作形态」与「激励结构」也降到物理。**

## 一、单写者 + 多读者：多题并发的适配方案

### 1.1 为什么不是"多写者分域"而是"单写者+多读者"

Cognition（Walden Yan, 2025-06）已更新结论："multi-agent systems work best today
**when writes stay single-threaded** and the additional agents contribute intelligence
rather than actions"。阶段 2 的 worktree 车道解决的是「物理互踩」，但没解决「决策分散」：
两个车道各自在局部上下文做局部最优解题决策，合入才第一次看见对方。

P2 的正确形态不是"多写者各占一域"，而是：

```
                ┌─────────────────────────────────┐
                │  orchestrator（唯一写者）         │
                │  解题决策 / flag 记录 / solved_by │
                │  台账 / KPI / 提交与合入          │
                └───────┬─────────────────────────┘
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
  worker(只读)    worker(只读)     Reviewer(只读)
  presolve/工具   读题库/读skill    读 diff/跑回归
  LLM 出候选      跑靶机探测        语义审查
```

### 1.2 回应三个追问

**Q1：单写者会不会变成多题并发的瓶颈？**
不会——瓶颈判断要区分「写冲突」与「计算并行」：
- 多题并发的真正并行发生在 **worker 层**（presolve / 工具链 / LLM 出候选），这些是**只读计算**，天然可并行；
- orchestrator 的"写"只有三件小事：flag 落账、solved_by 归属、提交合入——每次都是 O(1) 记录，
  不是解题主链路。**单写者串行化的是"写"，不是"算"**；
- 对比：当前"多写者分域"把每个会话的写都放行，合入时才碰撞——串行化发生在最贵的时刻（合入回溯）；
  单写者把串行化压到最便宜的时刻（记账）。这是"删一步 > 加固一步"在协作形态上的应用。

**Q2：多读者的"智能贡献"怎么落地到解题流程？**
两种落地，都是只读：
- **worker = 只读解题器**：读题库/读 skill/跑工具/调 LLM 出候选 flag，把候选**写回一个只读可见的
  inbox 文件**（`data/results/candidates_<task>.json`），orchestrator 单点校验后决定落账与否。
  → 对应现有 `presolve` 层（13/15 命中）的扩展：presolve 从"函数内直出"升级为"可并行 worker 出候选"。
- **Reviewer = 只读审查者**：读 diff/跑回归/语义审查，输出评审结论（不写文件）。
  → 对应现有 `_reviewer_gate.py` 的扩展：从"合入前一次性"扩展为"解题中按需"。
- 落地接口：`scripts/_session_boot.py` 增加 `--readonly` 模式——**物理限制**：
  只读 worker 启动时检查 `git diff` 为空、`git status` 无写意向，且**不 acquire 写租约**、
  不提交不推送（配合 pre-commit ③ fail-closed，无租约的提交默认拒绝）。

**Q3：3 个靶机槽位的并发限制和单写者架构怎么协同？**
靶机槽位是**资源配额**，不是写冲突——两者正交：
- 槽位调度在 worker 层（orchestrator 把最多 3 个靶机任务分给 3 个只读 worker 并行占槽）；
- 槽位结果（flag/失败原因）由 worker 写 inbox，orchestrator 统一消费；
- 当前 `_session_boot.py` 的冒烟检查 + 车道隔离已保证"不会有两个写者抢同一靶机目录"，
  单写者架构下这个保证从"约定"变成"结构"：只有 orchestrator 持有写权限。

### 1.3 最小可行实现（不重构核心解题逻辑）

| 层 | 改动 | 涉及文件 | 影响 |
|---|---|---|---|
| 只读模式 | `--readonly` 启动开关：无写租约 + 冒烟检查 diff 干净 | `scripts/_session_boot.py` | 新增参数，不破坏现有 |
| 候选 inbox | worker 出候选写 `data/results/candidates_*.json`（只读消费者=orchestrator） | 新增 `scripts/_candidates.py`（或复用 goal_log 结构） | 新增文件 |
| 单点落账 | orchestrator 校验候选 → 写 solved_by/flag → 提交 | 现有 `_merge_gate.py` + `REAL_SOLVES_LEDGER.md` 流程 | 复用 |
| 看板 | `_board.py` 展示"orchestrator 单写 + N 只读 worker"当前状态 | `scripts/_board.py` | 渲染扩展 |

**不做**：不引入新框架（无 orchestrator SDK、无消息队列）——用 git + 文件系统 +
现有闸门就够，符合"零新框架"原则。

## 二、激励结构物理锚点：把「如实记录不变」变成机器规则

### 2.1 问题重述

评分反馈核心缺口：技术拦截防得住「故意造假」，防不住「激励驱动的无意识造假」——
"数字变大获得的赞赏远高于如实记录不变"，赶时间的会话会为出成果而生产好消息。
宣言（AGENTS.md 三铁律 + 组织规则"如实与解出同级表扬"）本身不可强制，
需要**物理锚点**：让"诚实"在机器层面获得与"解出"同等的可量化正反馈。

### 2.2 三个可落地的物理锚点

**锚点 A：看板默认排序 = 连续如实记录天数，而非解出数**
- 现状：`_board.py` 按分支/任务渲染，排序未定义。
- 改动：看板主视图默认按「该分支最近 N 次合入中，KPI 记录如实（无虚增）的连续次数」降序；
  解出数只作第二排序键。
- 效果：会话的"可见荣誉"不再只绑定解出数——如实记录不变的分支排在前面，
  激励从"生产好消息"转向"保持记录可信"。
- 采集：`git log` 的 commit message + `REAL_SOLVES_LEDGER.md` 变更 diff（`_board.py` 可读）。

**锚点 B：0 新增但如实的 commit 走合并绿色通道**
- 现状：`_merge_gate.py` 对每次合并跑 KPI 断言（≥基线）+ 全量测试——「如实记录不变」的
  commit 与「解出新题」的 commit 走同一道闸门，没有区分。
- 改动：`_merge_gate.py` 增加 `--honest-zero` 分支：满足 ①KPI 计数 = 基线（无降）②真值回归集
  全过（`regression_check`，P0-1 已实现）③诚实扫描通过（`_honesty_scan.py`，已有）时，
  给该合并打一个**机器标记**（commit message 追加 `honest-zero: yes`），
  看板把它渲染为"诚实记录"徽章，与"新解出"徽章同级。
- 效果：诚实不涨数字的合并在机器层面获得**可量化的正反馈**（徽章 + 看板排序），
  不再是"淹没在一堆 feat 里"。
- 实现：复用 P0-1 的 `REGRESSION_CHECKS` + `count_offline_verified`，零新依赖。

**锚点 C：KPI 计算加入「稳定性权重」**
- 现状：KPI = offline_verified 计数（单调不降断言）。
- 改动：`_board.py` 计算 `stability_score = 1 - (近 N 轮 benchmark 解出率的标准差 / 均值)`，
  KPI 展示 = `offline_verified × (1 + stability_score × α)`（α 建议 0.1，可调）。
- 效果：同样 13/15 的两次跑分，波动大的排在波动小的后面——"稳定地不造假"
  比"偶尔冲高"获得更高排名，直接对齐「量尺的公信力取决于组织如何对待坏消息」。
- 采集：`data/results/benchmark_*.json` 的历史 `solved` 序列（P1 已规划落盘）。

### 2.3 物理锚点 vs 宣言（对照表）

| 维度 | 宣言（已存在） | 物理锚点（P2 新增） |
|---|---|---|
| 如实记录 | AGENTS.md 组织规则："与解出新同级表扬" | 看板排序键 A + 绿色通道徽章 B + 稳定性权重 C |
| 坏消息 | "先念不变的那批"（人执行） | `--honest-zero` 机器标记 + 看板徽章（机器执行） |
| 防无意识造假 | 诚实扫描（拦截假水位） | 稳定性权重（让"波动大"在排名上吃亏，无需判定意图） |
| 防故意造假 | 合并闸门 KPI 断言（拦截） | 回归集真跑（P0-1，拦截台账与现实的脱钩） |

## 三、落地顺序

| 优先级 | 动作 | 涉及文件 | 验证 |
|---|---|---|---|
| P2-1 | 看板排序键 A + 稳定性权重 C | `scripts/_board.py` | 渲染顺序变化可复现 |
| P2-2 | 合并绿色通道 `--honest-zero` + 徽章 | `scripts/_merge_gate.py`、`_board.py` | 合入一次"如实不变"分支，看板出徽章 |
| P2-3 | `--readonly` 只读模式 | `scripts/_session_boot.py` | 只读 worker 提交被拒（fail-closed 实测） |
| P2-4 | 候选 inbox | 新增 `scripts/_candidates.py` | 2 个只读 worker 并行出候选，orchestrator 单点落账 |

**不做**：不重构核心解题逻辑；不引入新框架；不改 benchmark 评测口径。

## 四、验收标准（P2 完成后可机检）

1. `_board.py` 渲染：默认按"连续如实天数"排序（脚本可断言排序键）；
2. `_merge_gate.py --honest-zero`：0 新增分支合入成功且 commit message 含 `honest-zero: yes`；
3. `--readonly` 模式：只读 worker 尝试 commit 被 pre-commit ③ 拒绝（exit 1）；
4. 稳定性权重：手工构造 2 组 benchmark 序列（稳定 vs 波动），看板排名稳定组靠前。
