## 三、核心结论

1. **stuck_loop 仍是主失败模式**（5/7），根因双类：
   - 无附件数值题（crypto-002/003、misc-006）：题目描述缺真实数据，模型无法实操——已通过补参数修复 crypto-006/007/008

2. **幻觉 flag 拦截有效**（web-005、crypto-006）：模型给出的 flag 与题库不符被 is_correct 拦截，验证防幻觉体系工作
3. **单题耗时偏高**（36-205s）：全量 40 题按此速率约需 40-60 分钟，8/14-15 需分批续跑

### 5.12 🚨 0 解出根因修复：工具层从未接入真实模式（2026-08-16 重大发现）

**问题**：16 题 0 解出，用户质疑"太菜了"。定位根因——不是模型菜，是**系统 bug**：

`run.py` 的 `build_solver` 真实模式创建 `MainAgent` 时**只传了 llm_client/supervisor/checker，
漏传 registry（工具层）和 sandbox（沙盒）**。主 Agent 的 `_act` 中
`if action=="tool" and self.registry` 永远为 False → 模型即使 plan 想读附件/跑脚本，
也只会落到纯 reason 分支 → **整个真实跑分链路一直"无手无脚"**，工具层从没真正接进去。

**修复链（3 处）**：
| # | 文件 | 修复 |
|---|---|---|
| 1 | `run.py` build_solver | 构建 ToolRegistry（7 适配器）+ SubprocessExecutor，传入 MainAgent(registry=, sandbox=) |
| 2 | `core/main_agent.py` `_act` | tool 分支自动注入附件路径（模型说读附件但没给 path 时，从题目附件补上） |
| 3 | `core/main_agent.py` `_build_plan_prompt` | "已执行步骤" observation 截断 80→500 字符（附件参数完整进模型上下文） |

**修复后验证（crypto-006 RSA 小指数）**：
