## 一、盲区数据 → presolve 优化闭环（P1-1）

### 现状缺口
benchmark 报告 `results[].confidence` 字段已存在（数据结构就绪），但值恒为 0.0——
`solve_specialcurve2` 之类 LLM 链路没有在 AgentOutput 里返回 `confidence`。

### 闭环设计（四步，每步对应具体模块）

**Step 1：置信度输出管道（先决条件，最小改动）**
- `core/prompts.py` 的 `SOLVE_DISCIPLINE` 常量加一行："输出格式：每步以 `confidence: 0-100` 结尾，先报信心再动手（AFCE 思想：把自信变成可 grep 字段）"。
- `core/main_agent.py`（或 solver 返回处）从模型输出解析 `confidence` 写入 AgentOutput；
  benchmark 的 `BenchmarkResult` 已在 `eval/benchmark.py` 有 `confidence` 字段——只差填充。
- 验证：重跑 `python -m eval.benchmark --questions-dir data/questions_real --provider baidu,qwen`，
  检查报告 `results[].confidence` 非零且分布有区分度（简单题应 > 难题）。

**Step 2：盲区聚合脚本（`scripts/_blindspot.py`，新增）**
- 输入：`data/results/benchmark_*.json`
- 逻辑：`confidence >= 0.8 且 solved == False` 的题 = 盲区；按 category 聚合。
- 输出：`data/results/blindspots_<date>.json` + 看板一行（`_board.py` 加一列）。

**Step 3：盲区 → presolve 优化建议（半自动，脚本产出候选）**
- 盲区题的特征（题面/附件/error_struct）→ 对比 `skills/` 目录现有 skill 的 `trigger_keywords`：
  - 盲区题是 crypto 且现有 crypto skill 触发词没覆盖其关键概念 → 输出「skill 触发词补全建议」；
  - 盲区题无对应 skill 但 error_struct 显示"工具链缺失"（如 factordb 网络失败）→ 输出「fast_solve 模板补充建议」。
- 产出落盘 `data/results/presolve_hints_<date>.md`，**人工确认后**才允许进 skills/（避免幻觉进 skill）。

**Step 4：闭环反馈进 benchmark 基线**
- `_merge_gate.py --full-baseline` 跑完后，比较新旧盲区集：
  - 旧盲区在新一轮消失 → 正向证据（presolve 优化生效）；
  - 新盲区出现 → 看板告警（RDD 红线：只扩 skill 不涨解出 = 治理复发）。

## 二、7 步链路失败步统计（P1-2）

### 7 步链路定义（与 `goal_log.jsonl` 的 `error_struct` 对齐）

| 步 | 名称 | goal_log 可采集字段 |
|---|---|---|
| 1 | 平台轮询 | task_id 获取失败 / error_struct 网络段 |
| 2 | 分诊 | question_type 识别失败 / skill_require 为空 |
| 3 | 附件下载 | error_struct 附件段 / 无附件 flag 不一致 |
| 4 | presolve | solved_by=presolve 且 False / skill 未命中 |
| 5 | LLM 主 Agent | solved_by=main_agent_llm 且 False / confidence=0 |
| 6 | 校验 | validated=false 且 flag 非空（假 flag） |
| 7 | 提交 | 平台 accepted 失败（需赛时字段） |

### 统计脚本（`scripts/_chain_stats.py`，新增）
- 输入：`data/results/goal_log.jsonl`
- 逻辑：解析每行 `error_struct`，按"最远成功到达步"归类 → 输出各步失败率直方图。
- 产出：`data/results/chain_stats_<date>.json` + 看板一行。

### 处置原则（符合误差复利数学：删一步 > 加固一步）
- **失败率最高步**：优先「删除/降级」而非加固——
  - 若附件下载是瓶颈且 presolve 不需附件 → 降级：无附件直接跳 LLM；
  - 若 presolve 命中率 > 80% → LLM 步对已 presolve 命中的题直接跳过（省 token + 省一步误差）；
  - 若提交步（第 7）仅在正式赛存在 → 本地 benchmark 中删除该步（口径：本地只到校验）。
- **失败率次高步**：加固（重试/超时/降级 provider）。

## 三、度量阈值基线方案（P1-3）

### 原则
阈值必须有**今日实测基线**为锚，先跑一周历史数据定分布，再定阈值——
不拍脑袋给"5%""10%"，而是「基线 ± 容忍度」。

### 治理类（今日已有基线）

| 指标 | 今日基线 | 建议阈值（1 周数据后校准） | 采集路径 |
|---|---|---|---|
| 冲突率 | 本日 0 次覆盖（gu 抢先提交 1 次，属 pre-worktree 历史） | < 5%/周 | `git reflog` + coordination takeover_audit |
| 假水位拦截率 | 今日 0 拦截（commit-msg 全过） | 拦截/提交 < 20% | commit-msg 钩子日志 |
| 提交违规率 | 今日 0 拒绝 | < 10% | 钩子退出码采集 |
| 文档-现实漂移率 | 0（fail-closed） | 恒 0 | `_doc_consistency` |
| 治理摩擦成本 | **commit 级 0.71s / merge 级 29.89s**（实测） | commit < 3s，merge < 60s | 钩子计时日志 |

### 解题类（今日已有基线）

| 指标 | 今日基线 | 建议阈值 | 采集路径 |
|---|---|---|---|
| 真实解出率 | 13/15 (86.7%) benchmark；台账 5 offline_verified | 台账 ≥ 基线（闸门断言）；benchmark 单调不降 | `_merge_gate.py` |
| presolve/LLM 功劳占比 | presolve 13/13（100% 命中题），LLM 0/2 | presolve ≥ 50% 正常；LLM 独立贡献 < 20% 且 KPI 涨 = 假 KPI 告警 | benchmark solved_by 聚合 |
| 置信度-正确率偏差 | **不可算**（confidence 全 0，Step 1 未通） | 管道通后 ECE < 0.15 | benchmark confidence 列 |
| 链路平均失败步 | 待 `_chain_stats.py` 首跑 | 平均失败步 ≤ 4 | goal_log error_struct |
| 盲区检出率 | 待 Step 1 后首算 | 高置信错误 / 高置信总数 < 30% | benchmark 交叉分析 |

### 校准流程
1. 今日已立基线（上表"今日基线"列全部来自实测命令，可复核）；
2. 跑 1 周（每日 `--full-baseline` + `_chain_stats`），收集分布；
3. 阈值 = 分布 P90 值；若 P90 已越红线（如 merge > 60s），先优化再定阈值。
