## 二、为什么效果巨差：五层根因

### 根因 ①（致命）：DasCTF 真实 API 字段与代码假设错配 → Agent 拿不到题面/附件/靶机

这是 `0解出根因诊断-20260821.md` 已定位的真因，且**赛中未修复**：

```
list_challenges 真实返回：{id, name, order, isOpen, hasSolved} 仅 5 字段
代码假设：has_attachment / has_instance / description 存在
                              ↓
has_attachment=False 恒成立 → 附件永不下载（data/platform_downloads/ 为空）
has_instance=False 恒成立  → get_access 永不调用 → 靶机地址永远注入不了
description="" 默认空串     → LLM 拿不到题面
                              ↓
Agent 用空 description + 无附件 + 无靶机 构造 Question
                              ↓
LLM 无输入 → 监督 LLM 裁决"题目缺少附件或靶机地址"
                              ↓
连续失败 → 墙钟超时（150s/300s）→ 止损换题 → 下一题同样缺数据
                              ↓
62 题全部 attempted、0 solved
```

**实证**（goal_log 高频模式）：
- `misc` 题 5868 条记录中，能力缺口自报：`"misc题型缺少附件数据，可能需要靶机交互"` —— 说明 Agent 自己知道"没数据"
- `crypto` 题同样：`"crypto题型缺少附件数据"`
- 靶机地址字段 `endpoints[].exposeIps[0]`（如 `1.14.76.59:15445`）代码完全没解析

**结论**：这是**工程实现与平台真实接口未对齐**的硬伤。赛前 `--probe` 只验证了"能拉到题"，没验证"能拿到解题所需数据"。

---

### 根因 ②（严重）：Agent 87% 时间在"纯推理空转"，几乎不调用工具

从 goal_log 的 `what_i_did` 字段统计：

| 行为模式 | 次数 | 占比 |
|----------|------|------|
| `recon:reason; recon:reason; recon:reason`（纯推理×3） | 4187 | **56.3%** |
| `recon:reason; recon:reason`（纯推理×2） | 2295 | 30.9% |
| `recon:tool:file_analyze; recon:reason; recon:reason` | 284 | 3.8% |
| `recon:tool:file_analyze; recon:script; recon:script` | 185 | 2.5% |
| 无步骤记录 | 170 | 2.3% |
| `recon:script; recon:script; recon:script` | 87 | 1.2% |

**关键数据**：
- **全 7437 条记录中，仅 8.4% 调用了任何工具**（file_analyze / script / http_request / flag_scan）
- **87.2% 的记录是纯 LLM 文本推理（recon:reason），没有任何工具执行**
- 即使调用工具，也多是 `file_analyze`（看一下文件）而非 `script`（实际跑脚本解题）

**含义**：Agent 既没有数据（根因①），也没有主动执行攻击脚本的习惯。在"无题面+无附件"的绝境下，它选择了反复用 LLM 文本"思考"而非尝试下载/探测，本质是被空 Question 逼入死循环。

---

### 根因 ③（严重）：同一题反复尝试 8–12 次，墙钟止损形同虚设

`solve_progress.json` 的 attempts 分布：
```
6 次: 17 题
7 次: 15 题
8 次: 2 题
10 次: 5 题
11 次: 7 题
12 次: 13 题   ← 最高频，13 道题被尝试了 12 次
```

**问题**：
- 每题平均 8.4 次尝试，但每次尝试都是"拿空数据 → LLM 空转 → 超时 → 换题 → 再拿空数据"
- 墙钟止损（150s/300s）只是"放弃这道题去试下一道"，但下一道**同样缺数据**
- 等于 62 题 × 8 次 × 150s = 全场 3 小时全在无效循环，**没有任何一道题因为"多试几次"而解出**

**根因①不修，根因③只会放大浪费**——这不是"努力不够"，是"方向错了还在加速"。

---

### 根因 ④（管理）：赛前"100% 水位"是虚假繁荣，度量口径严重失真

赛前文档声称：
- `赛前攻坚实录`：真实水位 89% → 100%（9/9）
- `实战优化记录`：彩排 11/12 = 92%

**但实战 0%**。差距来源：

| 层面 | 赛前口径 | 实战真相 |
|------|----------|----------|
| 题库 | 15 道**历史真题**（玄盾杯2020/西湖论剑2021等） | 战场是**2026 新题**，非历史题 |
| 数据获取 | 本地 `data/questions_real/` 文件齐全 | 平台 API 字段错配，远程拿不到 |
| 度量源 | Agent 自报 `validated`（含 `flag{got_it_2026}` 占位符） | 平台 accepted = 0 |
| 环境 | 本地 Mock + 预先下好的附件 | 真实 API 动态题/靶机 |

**核心失误**：赛前**从未用真实平台 API 端到端跑过一道完整题**（从 list → get_detail → 下载附件 → 解题 → 提交）。`--probe` 只验证了"能拉题列表"，这是最低限度的连通性检查，不是功能验证。

---

### 根因 ⑤（架构）：题目分类与工具路由在"无数据"场景下完全失效

Agent 对 62 题的分类尝试：
- misc: 5868 条（79% 流量）
- crypto: 585 条
- reverse: 403 条
- web: 285 条
- pwn: 246 条

**异常点**：misc 占了 79% 的尝试量，但战场新题中 misc 不可能占 79%。这说明分类逻辑可能把大量"拿不到数据的题"全部归为 misc（因为 misc 是兜底类别），进一步证明根因①——**题面/附件缺失导致分类器只能瞎猜**。

**无论原因，结论是一致的**：赛前必须把"平台真实接口适配"作为**最高优先级 P0** 端到端验证，而不是赛中补救。

## 四、优化建议（按优先级）

### 🔴 P0 — 决赛前必须修复（否则决赛同样 0 分）

**P0-1：端到端平台适配验证（最重要）**
- 写一个 `scripts/_e2e_verify.py`：从 list → get_challenge(id) → 解析 attachment/endpoints → 下载附件 → 打印"此题可解数据是否齐全"
- 赛前对**每类题型各抽 1 道**跑通，确认：附件下载成功、靶机地址解析正确、题面非空
- 把这个验证加入 `setup.sh` 的预检环节（当前 setup.sh 只检查环境，不检查数据链路）

**P0-2：修复 `get_access` 靶机字段解析（`dasctf.py:226`）**
```python
endpoints = data.get("endpoints") or []
for ep in endpoints:
    ips = ep.get("exposeIps") or ep.get("proxyIps") or []
    if ips:
        host, _, port = str(ips[0]).partition(":")  # "1.14.76.59:15445"
        if host: break
```
并把 `endpoints` 非空视为 `has_instance`。

**P0-3：solver 入口无条件拿完整 detail（`run.py:576`）**
```python
detail = await platform.get_challenge(ch.id)   # 真实 description/attachment/endpoints
ch = detail
```
拒绝用 list 阶段的残缺 `ch` 直接构造 Question。

**P0-4：无数据即止损，禁止空转**
- 若 `ch.description` 为空 **且** 无附件 **且** 无靶机 → 直接标记 `skipped_no_data`，不进入 LLM 循环
- 这能立刻把 87% 的无效 `recon:reason` 流量砍掉，节省墙钟给真正有数据的题

---

### 🟠 P1 — 架构与度量优化

**P1-1：工具调用率强制下限**
- 当前 8.4% 工具调用率太低。在 Plan-Act 循环加规则：**每题前 2 步必须至少调用 1 次 `file_analyze` 或 `http_request` 或 `script`**，否则监督 Agent 强制重定向
- 对"无数据"题，第一步应是"尝试下载附件 / 探测靶机"，而非"LLM 思考"

**P1-2：统一度量口径，杜绝虚假水位**
- 删除 Agent 自报 `validated` 作为进度指标，看板只显示"平台 accepted"
- 赛前彩排必须用**真实平台 API**（哪怕测试赛环境），不能只用本地 Mock 真题
- 诚实水位（纯 LLM 33%）写进答辩底稿，不夸大

**P1-3：分类器增加"数据可用性"维度**
- 当前 misc 占 79% 是因为无数据题全归 misc。增加 `has_data` 判断：无数据题直接走 P0-4 止损，不占分类流量

**P1-4：墙钟止损升级为"数据止损"**
- 当前止损只看时间。增加：连续 2 次 `reasoning_jump=false` 且 `last_error=stuck_loop` → 立即放弃，不浪费第 3–12 次

## 五、一句话总结

> **不是 LLM 不行，也不是 Agent 架构错，是"赛前没验证真实平台数据链路"这一件事，让所有工程成果在战场上归零。**
>
> 92% 的彩排水位建立在"本地真题 + 预下载附件"的温室里；0% 的实战结果暴露在"远程 API 字段错配 + 无数据空转"的寒风中。
>
> **决赛翻盘的唯一前提**：P0-1 到 P0-4 全部落地，且赛前 1 小时用真实平台跑通至少 3 道完整题（crypto 附件题 + web 靶机题 + misc 隐写题）。
