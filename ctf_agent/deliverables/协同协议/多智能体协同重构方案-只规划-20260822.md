## 0. 一句话方案

**先厘清：你的多智能体是真实存在的**——就是每天开的那一堆独立 LLM 会话，每一个都是独立运行的 agent，通过共享 git 工作树交互。这是**去中心化多智能体系统**（agents 独立运行、无中央编排器），不是伪的。缺的不是 agent，是 agent 之间的**协同层**。

把"协同层"降维成四个正交的工程问题分别解决：

| 子问题 | 学科 | 解 | 价值占比 |
|---|---|---|---|
| P1 并发控制：N 个写者如何不互踩且最大化并行 | 分布式系统（Lease/分区） | 目录级多写者租约 | **80%** |
| P2a 身份：谁在写、如何防撞名/冒充 | 密码学 | 唯一 ID 登记 →（可选）签名 | 10% |
| P2b 归因：谁贡献了什么 | 博弈论/度量 | 双权重贡献分 | 5% |
| P3 验收：写的东西对不对、能不能合并 | 软件工程 | Reviewer 单点门禁 | 5% |

**关键判断：这四个问题，没有一个需要 MARL，也不需要再多写一个"编排框架"。** 你的 agent 已经在独立运行了（这正是去中心化多智能体的特征），现项目的问题是把"协同层"揉成一个"CTDE 协同"，结果既没做对并发（单写者串行），也没做对身份（裸字符串），最后只剩一个 300 行的互斥锁。

## 1. 问题重定义：先回答"真实并行度到底是多少"

上一轮锐评说"单写者锁把吞吐压到 1×"。这里我要**更精确**，因为精确才能指导设计：

- **写操作**（`git commit`、落文件）：被单写者锁**串行化**，是真瓶颈。
- **读操作 + LLM 推理**（读题、读 skill、调用模型）：**天然并行**，锁根本管不着，也无需管。
- **CTF 题目之间的依赖**：绝大多数题 `data/<题id>/**` 互相独立，是 **embarrassingly parallel** 工作负载。

所以结论是：**单写者锁杀死的不是"解题计算"，而是"多会话同时沉淀 skill / 工具 / 题解"的写并行。** 而这一步恰恰是赛后最有价值的产出（把每道题的解法固化成 skill）。因此 P1 是真问题，值得做，但要说清楚它优化的是"写沉淀"的吞吐，不是"LLM 推理"的吞吐。

**由此得到一个判据：分区是免费的。** 因为题目天然按 `data/<题id>/**` 隔离，题目间无依赖，目录分区不需要任何人为设计——它已经躺在文件系统里了。这是本方案能做"目录级多写者"而不用纠结的根本原因。

  租约:           租约:           租约:                        (单 integrator)
  agents/**      skills/**       data/<题id>/**                 pytest+scope+签名
  密钥 Sa        密钥 Sb         密钥 Sc                         唯一 merge 入口

## 3. P1 并发控制（核心，80% 价值）

### 3.1 数据结构改造：单 session → 多租约映射

现实现（`_lease.py:134-143`）的致命点在 `coordination.json` 只存**一个** session：

```json
{"session": "A", "scope": ["agents/**"], "last_heartbeat": ..., "ttl_min": 30}
```

改造为**多租约映射**（接口草图，非实现）：

```json
{
  "leases": {
    "A": {"scope": ["agents/**", "tests/**"], "last_active": 1724330000, "ttl_min": 30, "key_id": "sa-..."},
    "B": {"scope": ["skills/**"],                "last_active": 1724330010, "ttl_min": 30, "key_id": "sb-..."},
    "C": {"scope": ["data/10793/**"],            "last_active": 1724330020, "ttl_min": 30, "key_id": "sc-..."}
  }
}
```

### 3.2 acquire 的相交判定（核心逻辑）

```
acquire(session, scopes):
    lock(coordination)                 # 原子锁不变（O_CREAT|O_EXCL 在 Windows 够用）
    for (other_session, lease) in leases:
        if other_session != session and not stale(lease):
            if scopes_conflict(scopes, lease.scope):
                return 拒绝(占用者=other_session, 冲突scope=交叠部分)
    leases[session] = 新建租约
    unlock()

scopes_conflict(a, b) -> bool:
    # 两两 fnmatch 交叠判定；注意 ** 的语义：
    #   "agents/**" 与 "skills/**" 不相交 → False
    #   "data/**" 与 "data/10793/**" 相交 → True
    #   "data/10793/**" 与 "data/10794/**" 不相交 → False
    return any(path_intersects(x, y) for x in a for y in b)
```

**语义关键**：拒绝的理由从"有人持锁"变成"**你要写的 scope 和别人存活租约交叠**"。A 持 `agents/**`，B 要写 `skills/**` → 放行（并行）。B 要写 `agents/foo/**` → 拒绝（交叠）。

### 3.3 粒度选择：写耦合度聚类（本方案最有价值的洞见）

"按目录分区"不是拍脑袋按现有目录树切，而是按**写耦合度**切。度量方法：

1. `git log --name-only` 导出历史所有 commit 的文件集合。
2. 构建**文件共现矩阵**：文件 i 和 j 出现在同一 commit 的次数。
3. 对共现矩阵做聚类（贪心/谱聚类），得到的**簇 = scope**。

道理：经常被一起改的文件（如 `core/main_agent.py` 与 `core/prompts.py`）应划进**同一 scope 交给同一个 worker**，否则两个 worker 会高概率冲突；而几乎从不一起改的文件可以放心分到不同 scope 提升并行度。

**这是"目录级租约"从"按目录"升级为"按耦合"的关键一步**，也是可发表的工程点——现有 LLM 多智能体框架没有谁用"写耦合聚类"来定租约粒度，都是人工拍目录。

### 3.4 活跃心跳 vs 提交心跳（修上一轮 D3）

现实现心跳只在 commit 时续租（`_lease.py:237`），长任务 >30min 未提交即被误判 stale。改造：

- `last_active` 与 `last_commit` **两个时间戳分离**。
- worker 每个"动作循环"（解一步、调一次 LLM）调 `heartbeat --session X`，刷新 `last_active`。
- TTL 判定用 `last_active`（活跃即不死），**stale 判定用"既无活跃又无提交"**。
- `--force` 接管仍保留 `takeover_note` 留痕，但接管前**二次确认**对方确实无活跃（读 `last_active` 而非 `last_commit`）。

### 3.5 fail-closed 默认（修 `_lease.py:222` 无租约放行）

现实现无 `coordination.json` 时放行（单人环境假设）。多会话环境下应**默认拒绝**：

- `leases` 存在但本 session 无租约 → 拒绝。
- `coordination.json` 不存在 → 仅当 `CT_AGENT_SINGLE=1` 放行，否则提示先 acquire。

## 4. P2a 身份：分层设计（先 ID 后签名）

**先问威胁模型**：这里没有恶意攻击者，只有会犯错、会撞名、会忘记登记的队友。所以身份层要解决的是**"误认/撞名"**，不是**"恶意冒充"**——这两者对安全强度的要求差一个数量级。

分层（每层独立、按需上）：

1. **L1 唯一 ID（必做，几乎零成本）**：会话启动时生成 `crypto-random` 的唯一 session id，写入 `coordination.json` 的 `key_id` 字段 + TOP-0 身份表。杜绝"糖露星霜•暖霞拾光"这种随手花名导致的撞名。
2. **L2 登记绑定（必做）**：session id ↔ 本次任务 scope ↔ 启动时间，写入 TOP-0 身份表。让"谁在写什么"可审计。
3. **L3 签名身份（可选，冻结期不做）**：`git config user.signingkey` + `commit.gpgsign`，或轻量 HMAC。pre-commit 校验签名会话 == 租约会话。

**什么时候才值得上 ECDSA（即 CCF 项目那套 CA-less 身份）**：只有当"会话之间互不信任、且有人有动机冒充别人提交"时才需要。**当前项目没有这个动机，上 ECDSA 是过度工程。** 上一轮锐评批评"身份是裸字符串"，精确的修法不是一步到位上 ECDSA，而是 L1+L2 先堵住"撞名/误认"，L3 留到"无人工干预的公开协同"场景再上。

## 5. P2b 贡献归因：拆成两种权重，别混用

上一轮我指出"贡献加权"会被"accepted 解出"偏向秒解题。这里给出精确解法：**两种权重分开**。

| 权重 | 用途 | 定义 | 何时可用 |
|---|---|---|---|
| **merge 权** | 冲突时谁的版本优先 | 验证通过的提交数（pytest 绿 + scope 内） | 现在就可算 |
| **归因权** | 复盘"谁在有效产出 vs 谁空转" | 最终存活代码行数 + 真实 accepted 解出 × 难度系数 | 需 accepted 数据，当前平台已关无法校准 |

**诚实约束（必须写进结论）**：归因权的"难度系数"和"accepted 解出"在当前无赛可打时**无法校准**，所以归因权只能做"相对排序"，不能做"绝对分数"。不要假装有一个能算出来的贡献分。

## 6. P3 验收门禁：Reviewer 单点 integrator

唯一 merge 到 main 的入口，**机器可执行、可回滚**：

1. `pytest -m "not slow"` 全绿（代码改动）。
2. 提交全部落在租约 scope 内（hook 已拦）。
3. 密钥扫描过。
4. （比赛期）flag 被平台 accepted。
5. 冲突回滚策略：merge 失败 → 保留 feature 分支 + 记录冲突文件，交回 worker，**不做自动三方合并**（自动合并是"写对不对"无人兜底时最大的坑）。

Reviewer 是**单点 integrator**，不是"多 agent 互审"——避免辩论式收敛成本（这是对上一轮方案的坚持）。

## 7. 编排层：为什么不上全职 Orchestrator（反共识判断）

Anthropic 报告说 orchestrator-worker 比单 agent 高 90.2%——但那是**需要跨文件协同的复杂工程任务**。CTF 解题是**天然可分区 + 高度动态**的场景，全职 LLM orchestrator 在这里是**净负担**：

1. 任务分解不如"按题号天然分区"准——不需要一个 agent 来"想"谁解哪题。
2. orchestrator 本身烧 token，且成为单点瓶颈。
3. 赛后收尾阶段，任务 = "把 62 题的解法固化"，这是**声明式清单**，不是需要动态决策的 DAG。

所以编排层退化为：**一个声明式任务板（TASK_BOARD）+ 一个薄调度脚本（读任务板 → 派发 scope → 调 worker）**。不引入会"思考"的编排 agent。这是对"CTDE/Orchestrator 崇拜"的刻意降温——**多数"多智能体"失败，不是缺编排，是编排得太重。**

## 8. 治理收口：诚实口径工程化

### 8.1 测试基线：单一事实源 = CI 报告，文档不抄数字

上一轮实测发现：文档钉死"208 passed"，磁盘全量跑是 206 passed + 2 errors（flaky）。根因是**硬编码数字必然漂移**。修法：

- 文档里删除一切"208 passed / 164 passed"这类数字，改为"见 CI 报告链接"。
- 修 flaky：`test_web_dashboard_persistence.py` 全量跑 FileNotFoundError（测试间耦合，依赖某个前置 fixture 的临时文件）。**修测试隔离，而不是修数字。**

### 8.2 在飞改动：从"靠自觉"到"收尾脚本强制"

- 收尾动作（用户喊停 / 会话结束）跑一个 `--closeout` 脚本：检查 `git status --porcelain`，有 M 文件则要么持租约提交、要么 `git checkout --` 回退，**脚本退出码非零即未收尾**。
- 根目录几十个 `_probe*.bin` / `_png33_*.bin` 是手搓 bkcrack 的残留（违反作战纪律 R1），**收尾脚本顺带扫描"根目录未跟踪临时文件"并提醒**。

## 10. 科研增量与诚实局限

### 真正的可发表点（去中心化多智能体 + 协同协议）

你确实有一个多智能体系统——**去中心化会话群**（N 个独立 LLM agent 共享 git 工作树、无中央编排器）。这不是伪命题，反而是**比"有中央编排器的多智能体框架"更接近生产现实、也更少被研究**的一类。

可发表的命题不是泛泛的"多智能体 CTF"，而是：

> **"去中心化 LLM 会话群上的协同协议：目录级多写者租约 + 写耦合度聚类定粒度 + 会话身份 + 贡献归因"**

这是**没人做过的窄命题**：工业界谈 multi-agent 大多默认"一个进程里有中央编排器"，而你的是"多个独立进程/会话通过共享仓库协同"——后者才对应真实世界"多个 AI 会话同时在一个仓库上干活"的场景。且可对照初赛"无租约 0 解出 + 互踩事故"天然基线做实验。指标：冲突次数、有效 merge 数、并行存活租约数、每题耗时。

### 诚实局限（必须写进任何结论）

1. 租约解决"谁在写、写哪不冲突"，**不解决"写对不对"**——由 Reviewer 门禁兜底，门禁误判仍会漏。
2. 归因权依赖 accepted 数据，当前平台已关，**只能做相对排序，不能做绝对分数**。
3. 本方案的价值已被确认（你每天确实开一堆并发会话），但**前提是这些会话真的在"同时写"**；若它们只是轮流排队、或实际只有一个人在动代码，P1 的并行收益仍会落空——所以第一步不是改架构，是**量化当前并发写冲突的真实频率**。
