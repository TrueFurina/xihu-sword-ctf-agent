## 1. 问题定义：这到底是什么问题

CTF-Agent 需要多个独立 LLM 会话同时工作，但**共享同一份 git 工作树与同一批核心文件**。初赛真实战绩 **0 解出**，复盘根因之一是「多会话无锁并发」——互相覆盖、在飞改动（改不提交）、门禁被删数据打红。

从科研视角，这个问题的**本质不是 MARL 训练问题，而是分布式系统里的并发控制 + 信用归因问题**：

- 动作空间（写文件）**完全重叠**，多个 agent 对同一资源竞争写。
- 没有天然"价值函数"可反传（代码协作不是回合制奖励学习）。
- 需要回答三个问题：**谁在写（身份）**、**写哪里不冲突（分区/租约）**、**写对不对（验收）**、**谁贡献了什么（归因）**。

这与 MARL 的核心难题一一对应，但**不是 CTDE 能直接套用的地方**（见 §2.1）。

## 2. 理论锚点（来自 `E:\Program\MARL` 的研究资产）

### 2.1 CTDE 的范畴错用（本项目的根本术语错误）

CTDE（Centralized Training with Decentralized Execution）是 MARL 的**训练范式**：训练期用集中 critic 学全局价值函数（解决信用分配 / non-stationarity），执行期各 agent 拿局部观测独立决策（MADDPG / QMIX / COMA / MAPPO 均属此）。

- 它的"分散执行"有一个**隐含前提**：agent 的动作空间天然不重叠（各控制一个实体/一个槽位）。
- 本项目所有会话的动作空间（写文件）**完全重叠**，照搬"分散执行"必互踩——这正是初赛事故的机理。
- 结论：**CTDE 是错误的概念容器**。本项目要的是"**协作式代码生产的编排 + 并发控制**"，对应的是**LLM 多智能体编排范式 + 分布式租约**，不是 MARL 训练。

### 2.2 你的 CCF 工作（CW-PBFT）才是正确的透镜

`marl-ecdsa-consensus-chain`（CW-PBFT 贡献加权共识 + ECDSA 身份 + SecurityGuard + 纳什均衡证明）里真正可迁移的四样东西：

| CCF 项目概念 | CTF-Agent 协同应映射为 |
|---|---|
| **ECDSA 链上身份**（无 CA，公钥注册） | **会话加密身份**：每会话一把密钥，commit 签名，杜绝"匿名/撞名"会话 |
| **贡献加权共识（Shapley 三公理）** | **贡献加权 merge/review**：按"验证通过的提交 + 真实解出"给会话加权，决定 merge 与仲裁权重 |
| **SecurityGuard 三层防御** | **hook 三件套**：密钥扫描 / scope 校验 / 身份校验，机器拦截 |
| **反背叛激励（selfish → 0% 背叛）** | **在飞改动禁令 + 接管留痕**：约束会话"改不提交 / 抢锁"的背叛行为 |

**一句话**：你已经在另一个项目里证明过"多智能体协同 = 身份 + 贡献加权 + 机器防御 + 博弈均衡"。CTF-Agent 应该把这套思想从"区块链共识"翻译成"代码仓库协同"，而不是生搬 CTDE 术语。

### 2.3 LLM 多智能体协作机制谱系（`Multi-Agent Collaboration Mechanisms A Survey of LLMs.pdf`）

主流协作模式（本项目应对号入座）：

1. **层级式（Orchestrator–Worker）**：一个编排者拆任务、派给 workers，workers 不互相通信 —— Anthropic 2025 生产实践：多 agent 协作比单 agent 高 90.2%，但 token ×15。
2. **辩论式（Debate）**：多 agent 对同一结论互辩，收敛到一致 —— 适合"方案评审"，不适合"并行写代码"。
3. **流水线/角色式（MetaGPT SOP）**：按固定 SOP 分工（产品→架构→编码→测试）—— 适合有固定工序的任务，CTF 解题工序不固定，故不适用。
4. **动态团队**：按需组建子团队 —— 灵活性高，但协调成本高、易失控（本项目的反面）。

**本项目适配**：以 **Orchestrator–Worker** 为主干（任务分解 + 目录分区），**Reviewer 门禁**为验收，**不引入辩论/动态组队**（避免重演"多会话无锁乱撞"）。Cognition 反方实证也提示：写代码上下文不可切片，worker 必须在自己的目录树内拿到完整上下文——这正是"目录级租约"的由来。

### 2.4 分布式系统经典

- **Lease（Gray & Cheriton 1989）**：租约 + TTL + 心跳，是"持锁者崩溃不死锁"的标准解。本项目 `_lease.py` 已用（方向对），但心跳只挂 commit（见 §3.3 D3）。
- **乐观并发（Git 本身）**：分支 + 合并 = 天然乐观并发。**本项目退而求其次用悲观租约，是因为"合并冲突"在无人工场景下代价高**——这是合理的工程取舍，但代价是牺牲并行度（见 §3.3 D1）。
- **资源分区 vs 全局互斥**：多智能体的目标应是"**不相交资源分区上的并行**"，而不是"全局同一时刻只准一个人写"。前者吞吐 = N×，后者 = 1×。

### 3.2 已核实为真的部分（不重做）

- 测试基线真实：`pytest -m "not slow"` = **208 passed / 1 skipped / 2 deselected（37s）**，实测通过。
- 自动记录机制真实：`core.hooksPath=git_hooks`，post-commit/post-merge 已装且真实写入总账。
- 诚实口径（platform accepted 唯一判据）落地到位。

### 3.3 关键缺陷（按严重度，`file:line` 实证）

#### 🔴 D1（P0）单写者全局互斥锁，不是"目录级多写者租约"

**声称**：纲领 §3「scope 取目录级、互不相交的分区」；协议 §一「Decentralized 各会话只在自己认领的文件域内执行，互不交叉」——即多个会话**并行**各写各的目录。

**实测**：`scripts/_lease.py:120`
```python
if cur and cur.get("session") != session and not is_stale(cur):
    print("写者租约已被 ... 持有"); return False
```
`coordination.json` 里只有**一个** `session` 字段（`_lease.py:134-143`）。只要 A 会话持有**任意** scope 的租约且未过期，B 会话无论要写哪个目录都会被拒。**同一时刻只能有一个写者。**

**结论**：这不是"目录级多写者租约"，而是**全局单写者互斥锁**。所谓"分散执行 / 并行解题"在实现里是**串行化**的——A 持有 `agents/**` 时，B 连 `skills/**` 都写不了。这直接推翻了"CTDE 分散执行"这一核心宣称，也杀死了多智能体的存在意义（并行加速）。

**根因**：设计者把"防冲突"简化成"一次只许一个人写"，把"动作空间分区并行"降级成了"互斥串行"。

#### 🔴 D2（P0）pre-commit 事前门禁未装进生效路径

**实测**：`core.hooksPath = git_hooks`，但 `git_hooks/` 里**只有 post-commit、post-merge，没有 pre-commit**。真正的双门禁脚本在 `scripts/hooks/pre-commit`（密钥扫描 + 租约 scope，代码完整、依赖 `_scan_secrets.py`/`_lease.py` 均在），却**全仓零引用**、未被 `setup.sh`（只装 post-commit/post-merge，`setup.sh:64-71`）装进去；另有一份 11:13 的陈旧 `.git/hooks/pre-commit` 被 hooksPath 覆盖失效。

**结论**：执法层里**唯一"事前拦截"的一环当前是死的**——治理实际是"事后记日志"，不是"事前拦提交"。总账反复声称"双门禁就位"与事实不符（已由另一会话承接修复，本稿不再展开）。

#### 🟠 D3（P1）心跳只挂 commit，无活跃度心跳 → 误判 stale

`_lease.py:237` 续租只在 `precommit`（提交时）发生；`heartbeat` 命令（`:159`）存在但**需手动调用，无后台自动**。后果：一个会话**持续工作但 30 分钟没提交**（长题很常见），租约到期被判 stale，另一个会话可 `--force` 抢占 → 正在写的东西被接管覆盖。TTL 兜底本意是防崩溃死锁，却因"心跳≠活跃"变成误伤活人。

#### 🟠 D4（P1）身份是裸字符串，无加密身份

`CT_AGENT_SESSION` 是任意字符串，可撞名、可冒充、无法审计（`scripts/hooks/pre-commit:29-32` 只读环境变量 / git config）。对比你自己的 CCF 项目用 **ECDSA 公钥注册做 CA-less 身份**，这里是明显的退步。多智能体协同若连"谁是谁"都无法防伪，租约门禁可被同名会话绕过。

#### 🟠 D5（P1）无贡献加权 / 信用归因

现有门禁是**二值的**（绿/红），没有"谁贡献了多少"的加权。你的 CCF 项目恰恰用 **Shapley 贡献加权**（CW-PBFT）解决"多智能体里功劳怎么分、权重怎么定"。CTF-Agent 缺这一环 → 无法区分"高效解题会话"与"空转烧 token 会话"，协调者的仲裁没有量化依据。

#### 🟡 D6（P2）无 merge / 冲突合并策略，靠协调者 ad hoc

单写者锁回避了 merge 冲突，但也因此没有"多 worker 分支并行 → Reviewer 合并"的流水线。协议 §四「冲突仲裁」全由协调者人工裁决，没有机器可执行的合并/回滚策略。一旦想放开并行，这里会立刻成为新瓶颈。

### 3.4 合理性评级

- **作为"安全底座"**（防密钥泄露 + 防无锁互踩 + 事后可追溯）：**合理，8/10**。
- **作为"多智能体协同范式"**（声称的 CTDE 分散并行执行）：**不合理，3/10**——术语错用 + 实现串行 + 身份/归因缺失。

## 4. 建议架构（方案 · 只规划）

### 4.0 总图

```
                    ┌─────────────────────────────────────────────┐
                    │   Orchestrator（编排器，单点，Gu 角色）        │
                    │   任务 DAG 分解 · 目录分区 · 验收门禁 · 合并裁决 │
                    └──────┬──────────────────────────┬───────────┘
                派发(目录scope)                        │ 验收/归因
        ┌──────────────────┼──────────────────┐        │
        ▼                  ▼                  ▼        ▼
   ┌─────────┐       ┌─────────┐       ┌─────────┐  ┌──────────────┐
   │ Worker A │       │ Worker B │       │ Worker C │  │  Reviewer    │
   │ 租约:     │       │ 租约:     │       │ 租约:     │  │ (单integrator)│
   │ agents/** │       │ skills/**│       │ data/**  │  │ pytest+accepted│
   │ 密钥SA    │       │ 密钥SB    │       │ 密钥SC   │  │ + 贡献加权merge│
   └────┬─────┘       └────┬─────┘       └────┬─────┘  └──────┬───────┘
        │  并行写各自目录树（互不相交分区）          │            │
        └──────────────┬──────────────────────────┘            │
                       ▼                                       ▼
        ┌───────────────────────────────┐        ┌──────────────────────────┐
        │ 执法层 git_hooks/（机器强制）      │        │  合并回 main（唯一入口）    │
        │ pre-commit: 密钥扫描+scope+身份   │        │  贡献加权 + 门禁全绿才放行   │
        │ post-commit: 自动记账 + 活跃心跳    │        └──────────────────────────┘
        └───────────────────────────────┘
                         │
                         ▼
        ┌───────────────────────────────────────────────┐
        │ 事实源：协同任务总账 TOP-0（身份→贡献→commit 全可追溯）│
        └───────────────────────────────────────────────┘
```

### 4.1 编排层：Orchestrator + 任务 DAG

- 单一协调者把"解题/攻坚"分解成**互不相交的目录 scope**（如 `agents/**`、`skills/**`、`data/<题id>/**`），按 DAG 派发，而不是平铺任务板。
- 协调者**不代写代码**，只做路由 / 验收 / 仲裁（沿用纲领 §9，正确）。
- 任务粒度 = 一个目录分区，保证 worker 在区内拿到**完整上下文**（Cognition 反方实证的关键）。

### 4.2 执行层：把 `_lease.py` 从"单写者互斥"改成"目录级多写者租约"（核心改造）

- `coordination.json` 从单 `session` 字段改为 **`leases: { session -> {scope, heartbeat, ttl} }`** 的多租约映射。
- `acquire(session, scope)` 检查的是**本 scope 与其他存活租约 scope 是否相交**（用 `path_in_scope` 做两两交叠判定），不相交即放行——**A 持 `agents/**` 与 B 持 `skills/**` 可并行**。
- 相交 → 拒；stale → `--force` 接管留痕（保留现有 takeover_note 机制）。
- 这是把现有代码从"全局互斥"升级为"分区并行"的最小改动，其余 TTL/原子锁/接管逻辑全部复用。

### 4.3 身份层：会话密钥 + 签名 commit（映射你的 ECDSA 身份）

- 每会话一把密钥（本地生成，注册到 TOP-0 账本的"身份表"）。
- commit 用 SSH 签名（`git config user.signingkey` + `commit.gpgsign`，或轻量 HMAC 校验 hook）。
- pre-commit hook 校验**签名会话 == 租约会话**，杜绝裸字符串撞名/冒充。

### 4.4 执法层：hook 三件套 + 活跃心跳

- `git_hooks/pre-commit`（**必须装进生效路径**，修 D2）：① 密钥扫描 ② scope 校验 ③ 身份签名校验。
- `git_hooks/post-commit`（现有，保留）：自动记账 + **触发活跃心跳续租**（修 D3：把"提交即心跳"扩展为"每次 commit 续租 + 长任务可由 worker 显式 `heartbeat`"，并把 TTL 与活跃挂钩）。
- 无租约默认拒绝（修 `_lease.py:222` 的"无租约放行"——多会话环境下应 fail-closed，单人模式才放行）。

### 4.5 验收门禁：Reviewer gate（单 integrator）

- 唯一 merge 到 main 的入口：**pytest 全绿 + 提交全在租约 scope 内 + 密钥扫描过 + （比赛期）flag accepted**。
- 与现有 `--compete` 的 `_e2e_verify` fail-closed 对齐（AGENTS.md 十四）。
- Reviewer 是"单点 integrator"，不是"多 agent 互审"——避免辩论式收敛成本。

### 4.6 贡献加权层：CW-merge（映射你的 CW-PBFT）

- 每会话维护贡献分 = **验证通过的提交 + 真实 accepted 解出** 的加权累积。
- 用于：merge 冲突时**谁的版本优先**、仲裁时**谁的证据权重高**、复盘时**谁在有效产出 vs 谁在空转烧 token**。
- 这是本项目相对现有工作的**可发表增量**：现有 LLM 多智能体框架都是"单 agent + 人工评审"，本项目是"**多独立 LLM 会话 + 无人工干预 + 租约机器强制 + 贡献加权 merge**"的组合，且可对照初赛"无租约 0 解出 + 互踩事故"天然基线做实验。

### 4.7 通信：隐式共识，不广播

- 会话间**不直接消息通信**，全部通过"共享仓库 + TOP-0 账本"隐式同步（对应你资料里的《高效通信：隐式共识生成》）。
- 显式广播只保留给"终止信号 / 阻塞升级"，避免 N 会话广播风暴（SendMessage broadcast 成本 O(N)）。

## 5. 风险清单（P0–P3）

| 级别 | 风险 | 触发条件 | 缓解 |
|---|---|---|---|
| **P0** | 单写者锁使多智能体退化为串行（D1） | 两个会话同时认领不相交目录 | 改造 `_lease.py` 为目录级多写者租约（§4.2） |
| **P0** | 事前门禁未生效（D2），密钥/越界无拦截 | 任何 commit | 把 pre-commit 装进 `git_hooks/`（已交另一会话） |

## 6. 实验设计与诚实局限

**对照组**：初赛 3 天无租约（64 题 0 解出 + 多会话互踩 + 门禁被打红）——已是天然基线，无需重跑。
**实验组**：装"目录级多写者租约 + Reviewer 门禁"后，跑历史真题消化（questions_real / race_details 47 题回归集）。
**指标**：冲突次数、返工 commit 数、有效 merge 数、每题耗时、并行度（同时存活租约数）。
**统计**：Wilcoxon 符号秩检验（配对，非参，样本小）。

**诚实局限**（必须写进结论）：
1. 租约解决"**谁在写、写哪不冲突**"，**不解决"写对不对"**——假解/错解由 Reviewer 门禁兜底，门禁若判断失误仍会漏。
2. "贡献加权"若以"accepted 解出"为唯一权重，会**偏向工具链秒解的题**，低估"攻坚难题"的贡献——权重设计需再论证（可引入"难度系数"）。
3. 当前平台已关（token 40403、无赛可打），**上述实验的"accepted"项无法真实验证**，只能做离线回归——这是本方案当前最大的外部约束，也是为什么本稿只规划、不喊 Go。
